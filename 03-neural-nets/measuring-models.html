Measuring Models: Precision, Recall, F1

You asked for measurement and benchmarking to be a spine of this course — this page is where that spine starts. The vocabulary here (precision, recall, F1, thresholds, baselines) returns verbatim when we evaluate NER (M10), retrieval (M9.5, M12), and LLMs (M11.4). It's also the single most reliably-asked interview cluster in all of ML. Worth doing slowly and once.

Accuracy, and the lie it tells

Accuracy = fraction correct. Intuitive, and dangerously misleading the moment classes are imbalanced — which in real life is almost always. The canonical horror story: a spam filter on traffic that's 1% spam. A model that predicts "not spam" for everything scores 99% accuracy while catching zero spam. The number is high; the model is useless. Whenever one class is rare — fraud, disease, relevant documents, entities in text — accuracy mostly measures the imbalance, not the model.

The confusion matrix: where every prediction lands

Fix: stop averaging everything into one number and sort predictions into four boxes. Convention: "positive" = the rare/interesting class you're hunting.

Precision and recall: two questions, not one

precision = TP / (TP + FP)   ·   recall = TP / (TP + FN)
In plain words — memorize these as questions: Precision: "of everything I flagged, how much was right?" (trustworthiness of the alarms). Recall: "of everything out there, how much did I find?" (coverage of the hunt). Above: precision = 40/50 = 0.80, recall = 40/60 = 0.67 — the 99.7%-accuracy model suddenly looks mortal.

The two trade off through the model's decision threshold. A classifier outputs a score (3.2's probability); you pick the cutoff. Raise it → fussier alarms → precision up, recall down. Lower it → catch everything → recall up, precision drowns in false alarms. The threshold is a business decision wearing a math costume:

F1, and how to average across classes

F1 = 2 · (precision · recall) / (precision + recall)
In plain words: the harmonic mean — a strict average that stays low unless BOTH are decent (precision 1.0 with recall 0.01 gives F1 ≈ 0.02, not 0.5). One number for leaderboards; the P/R pair for actual decisions. Above: F1 = 2·(0.80·0.67)/(0.80+0.67) ≈ 0.73.

With multiple classes (say, NER's person/org/location), two averaging conventions: micro — pool all TP/FP/FN counts, then compute once (big classes dominate; equals accuracy in single-label settings); macro — compute F1 per class, then average the F1s (every class votes equally, so rare-class failure shows up). Reporting both is the grown-up move; quoting only the flattering one is the classic leaderboard sleight-of-hand to watch for.

Baselines: the vaccine against self-congratulation

A metric without a baseline is a number in a void. Before celebrating any model, price these two: the majority-class baseline (predict the most common label always — the "99% accuracy" trap quantified) and a cheap strong baseline — for text classification, TF-IDF + logistic regression, which is embarrassingly hard to beat on many tasks. If your fine-tuned transformer beats majority-class but not TF-IDF+LR, you've built an expensive way to underperform 2003. (Next page you'll build both and check.)

Real numbers

The spam example, complete: accuracy 99.7%, precision 0.80, recall 0.67, F1 0.73 — four numbers, one model, and only the last three tell the truth. For calibration elsewhere: strong NER systems hit span-F1 ≈ 0.93 on news (M10.1); a good RAG retriever hits recall@5 ≈ 0.85+ on clean domains (M9.5); and email spam filters in production run precision ≈ 0.999 with recall ≈ 0.95 — because one false positive (lost real mail) costs more than ten misses. Cost asymmetry decides the threshold, always.

Connect the dots

You've already lived this trade-off without the names: GLiNER's threshold parameter — the one you tuned by feel — is exactly this page's green slider. Raise it: fewer, surer entities (precision). Lower it: more, noisier ones (recall). In M10.2 you'll measure it properly with span-F1. And when M9.5 asks "did retrieval find the right chunk in the top 5?" — that's recall wearing its retrieval uniform (recall@k). One vocabulary, your whole stack.

Build: compute everything from raw counts, then verify
import numpy as np

def report(tp, fp, fn, tn):
    acc  = (tp + tn) / (tp + fp + fn + tn)
    prec = tp / (tp + fp)
    rec  = tp / (tp + fn)
    f1   = 2 * prec * rec / (prec + rec)
    print(f"acc {acc:.3f}  precision {prec:.3f}  recall {rec:.3f}  F1 {f1:.3f}")

report(tp=40, fp=10, fn=20, tn=9930)     # the page's example

# threshold sweep on synthetic scores — reproduce the slider:
rng = np.random.default_rng(1)
scores = np.concatenate([rng.normal(0.35, 0.13, 9900),   # clean
                         rng.normal(0.72, 0.13, 100)])   # spam
truth = np.array([0]*9900 + [1]*100)
for t in [0.5, 0.65, 0.8]:
    pred = (scores > t).astype(int)
    tp = ((pred==1)&(truth==1)).sum(); fp = ((pred==1)&(truth==0)).sum()
    fn = ((pred==0)&(truth==1)).sum(); tn = ((pred==0)&(truth==0)).sum()
    print(f"threshold {t}: ", end=""); report(tp, fp, fn, tn)

Watch accuracy barely move across thresholds while precision and recall swing wildly — the whole page's argument in one printout. Then check against sklearn.metrics.classification_report for the professional version.

If you remember one thing

Accuracy averages over a lie when classes are imbalanced. Think in the four boxes; ask precision's question ("when I flag, am I right?") and recall's ("do I find them all?"); remember the threshold trades one for the other according to your error costs; and never report a metric without its baseline. This vocabulary is the measuring tape for everything else in the course.

Interview questions

When is accuracy a misleading metric, and what do you use instead?

Under class imbalance: with 1% positives, always-predict-negative scores 99% while being useless. Use precision/recall/F1 for the minority class (plus the confusion matrix), PR curves across thresholds, and always compare to the majority-class baseline. Accuracy is fine when classes are balanced and errors cost the same — rare in practice.

Define precision and recall as plain questions, and give a case favoring each.

Precision: "of what I flagged, how much was right?" Recall: "of what exists, how much did I find?" Favor precision when false alarms are costly: auto-deleting spam, auto-blocking users, triggering pager alerts. Favor recall when misses are costly: cancer screening, fraud detection, legal discovery — flag liberally, review downstream. The threshold implements the choice.

Why is F1 the harmonic rather than arithmetic mean?

The harmonic mean punishes imbalance: precision 1.0 with recall 0.01 averages to 0.505 arithmetically (looks half-decent) but 0.02 harmonically (correctly terrible). Since gaming one metric at the other's expense is trivial (flag everything → recall 1.0), a useful single number must require both to be good simultaneously — exactly the harmonic mean's behavior.

Micro vs macro F1 — difference, and when each misleads.

Micro pools all TP/FP/FN across classes then computes once — dominated by frequent classes; a model that fails completely on a rare class can still score high. Macro computes per-class F1 and averages — every class equal, so it exposes rare-class failure, but can look harsh if some tiny class is inherently noisy. Report both; a large micro–macro gap is itself the diagnostic (it means performance is uneven across classes).

How do you choose a classification threshold in production?

From error costs, not defaults: estimate the cost of a false positive vs a false negative, sweep the threshold on validation data, and pick the point optimizing expected cost (or satisfying a constraint like "precision ≥ 0.99, maximize recall"). Revisit when class balance or costs drift. Saying "0.5 because that's the default" is the wrong answer; "0.5 is arbitrary — here's my cost analysis" is the right one.

Your new transformer classifier hits 91% accuracy. The interviewer asks: "Good?" What do you need to answer?

(1) Class balance — if 90% of examples are one class, 91% is barely above the majority baseline. (2) A cheap strong baseline — TF-IDF + logistic regression often lands within a few points on text tasks; beating it justifies the transformer's cost. (3) Per-class P/R/F1 — the aggregate can hide a dead minority class. (4) The cost structure — which errors hurt. "91% is uninterpretable without baselines and per-class breakdown" is itself the correct answer.
