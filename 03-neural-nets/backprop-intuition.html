Backpropagation, Intuitively

The training loop's beat ③ said "compute every parameter's blame" and moved on. This page opens that box. Backprop has a reputation as the scary math of deep learning; in truth it is one idea (M1.4's chain rule) plus disciplined bookkeeping. We'll do it with arrows and actual numbers — no symbol walls — and by the end you'll know exactly what loss.backward() does for a living.

The problem: who gets the blame?

A network makes an error. Somewhere among its 22 million parameters, some weights pushed the output toward the mistake, some away, most barely mattered. To apply M1.4's update rule we need each parameter's individual slope: "if this one knob nudged up, how much would the loss change?" Measuring that naively — nudge one weight, rerun the whole network, observe, repeat 22 million times — costs 22 million forward passes per training step. Backprop gets every slope in one backward sweep. That efficiency is why deep learning is possible at all.

The idea: blame flows backward through the pipes

M1.4's chain rule said: when effects pass through stages, sensitivities multiply (dial → heat → browning = 3 × 2 = 6). A network is exactly that — a pipeline of stages. So: start at the loss with blame = 1, walk backward, and at each stage multiply the incoming blame by that stage's local slope. Where paths merge, blames add. Every parameter reads off its final blame as the product of everything downstream of it. Watch it happen with real numbers:

Two bookkeeping rules complete the algorithm: where a value feeds multiple downstream paths, its blames add (it contributed to every path); and each stage's local slope was already computed during the forward pass and cached — this is why training needs so much memory (the "activations" bill in M7.2) and why the backward pass costs roughly 2× the forward pass in compute.

What autograd does for you

Nobody derives these slopes by hand anymore. PyTorch/JAX build a computation graph as your forward code runs — every operation records itself and its local-slope recipe. Then loss.backward() replays the graph in reverse, doing exactly this page's multiply-and-add blame arithmetic, depositing each parameter's slope in param.grad, and optimizer.step() applies the update rule. The three most-typed lines in deep learning — loss.backward(); optimizer.step(); optimizer.zero_grad() — are: run this page, run M1.4, clear the blame ledger for the next batch.

Real numbers

Cost accounting for one training step, industry rule of thumb: backward pass ≈ 2× the forward pass FLOPs (it computes both input-blames and weight-blames per layer), so training ≈ 3× inference per token — before adding optimizer state. The cached local slopes ("saved activations") are why a model you can run in 14 GB needs 50+ GB to train (precise ledger: M7.2). And gradient checkpointing (M7.3) is literally: throw away some cached slopes, recompute them during backward — trading this page's memory for compute.

Build: verify the blame math with PyTorch autograd
import torch

# this page's exact pipeline: w → ×x → bend → loss
w = torch.tensor(2.0, requires_grad=True)
x = 3.0
z = w * x                       # local slope w.r.t. w: 3
a = torch.sigmoid(z)            # a bend; autograd knows its local slope
loss = 2.0 * a                  # local slope: 2

loss.backward()                 # blame flows backward, exactly as animated
print(w.grad)                   # = 2 × sigmoid'(6) × 3 ≈ 0.0148

# why so small? sigmoid'(6) ≈ 0.0025 — you just witnessed a vanishing gradient!
# z=6 sits on sigmoid's flat shoulder. Try x=0.3 (z=0.6, steep region) and
# watch w.grad grow ~50×. The animation's 'flat bend crushes blame' — live.

One extra experiment: chain 10 sigmoids (a = torch.sigmoid(a) in a loop) and print w.grad — then swap in torch.relu and compare. The vanishing-gradient story, falsifiable on your laptop in 20 seconds.

If you remember one thing

Backprop = blame flowing backward, multiplying by each stage's local slope, adding where paths merge — the chain rule with a filing system, computing every parameter's gradient in one sweep. Its failure mode (long products shrinking or exploding) explains half of modern architecture design, including the residual connections at the heart of every transformer you use.

Interview questions

Explain backpropagation without heavy notation.

The forward pass computes the output and caches each operation's local sensitivity. The backward pass starts at the loss with gradient 1 and walks the graph in reverse: at each operation it multiplies the incoming gradient by that operation's local slope (chain rule), summing where a value feeds multiple paths. One backward sweep yields ∂loss/∂parameter for every parameter simultaneously — the efficiency that makes training million-parameter models feasible.

What causes vanishing gradients, and name four mitigations.

The backward gradient is a product of per-layer local slopes; when those are consistently <1 (sigmoid/tanh saturate at ≤0.25/≤1 and are near 0 on their shoulders), the product decays exponentially with depth — early layers receive ~no signal. Mitigations: ReLU/GELU activations (slope ≈1 in the active region), proper initialization (Xavier/He keep signal variance stable), residual connections (an additive path whose local slope is exactly 1 — gradient flows unimpeded), and normalization layers (Batch/LayerNorm keep activations in the steep region). Transformers use the last three simultaneously.

Why does training take ~3× the compute of inference, and much more memory?

Compute: forward pass (1×) plus backward pass (~2× — gradients w.r.t. both activations and weights per layer). Memory: backward needs each layer's cached forward activations to compute local slopes, so memory scales with depth × batch × sequence length, on top of parameters, gradients and optimizer state. Gradient checkpointing trades this: discard some activations, recompute them during backward — ~30% more compute for large memory savings.

What do loss.backward(), optimizer.step() and optimizer.zero_grad() each do?

backward(): runs reverse-mode autodiff over the recorded computation graph, accumulating each parameter's gradient into .grad. step(): applies the update rule (SGD/Adam) using those gradients. zero_grad(): clears the accumulated gradients — because PyTorch adds into .grad by design (useful for gradient accumulation), forgetting this line silently sums gradients across batches, a classic bug whose symptom is training that behaves like the learning rate keeps growing.

Why do gradients "add where paths merge"?

If a value influences the loss through several routes (e.g., a hidden activation feeding many next-layer neurons, or a weight-tied embedding used twice), the total effect of nudging it is the sum of its effects along each route — basic calculus of total derivatives. Practically this is why shared/tied parameters (like tied input/output embeddings in language models) receive summed gradients from all their uses.

Interviewer: "Could we train without backprop — say, by tweaking weights randomly?"

In principle yes (evolutionary strategies, random perturbation), and such methods exist for tiny or non-differentiable problems. But they estimate gradients with variance scaling with parameter count — hopeless at 10⁶–10¹¹ parameters — while backprop computes exact gradients for all parameters at ~3× forward cost. The honest framing: backprop is not conceptually necessary but is computationally the only game in town at scale (with RL — M8.4 — as the structured exception where the objective itself isn't differentiable).
