Quantization & the Inference Stack

An 8-billion-parameter model needs 16 GB in fp16 (M7.2's arithmetic) — yet people run it on laptops with 8 GB, via Ollama, at usable speed. The trick is quantization: storing each of those 8 billion numbers with fewer bits. This page is the intuition for what "4-bit" actually does to a number, why the quality loss is shockingly small, and a decoder ring for the format zoo — GGUF, GPTQ, AWQ — you meet the moment you try to run anything locally.

Precision is a number line's resolution

A weight is just a number, say 0.2734. Storing it in fp32 uses 32 bits — a number line with billions of notches, overkill for a value a noisy gradient descent (M3.3) only ever learned approximately. fp16 keeps plenty of notches. int8 gives each weight one of 256 notches; int4, one of 16. Quantization is snapping every weight to its nearest notch: each snap adds a tiny rounding error, the model's outputs blur microscopically, and in exchange the whole thing shrinks 4–8×. The miracle isn't that quality drops — it's how little, because a network of billions of redundant weights (M8.5's low-rank lesson: most of that precision was never load-bearing) averages the rounding noise away.

What survives, what breaks

Weights quantize gracefully — they're static, known in advance, and can be carefully blocked and scaled offline. Activations are harder: they're computed live, and transformer activations famously contain outlier channels — a few dimensions with values 100× the rest that carry outsized meaning; naively squashing them to 4 bits lobotomizes the model. That's why the standard recipe is "weights in int4, activations and KV cache in fp16, compute in fp16 after dequantizing on the fly" — you pay memory for weights (the biggest bill) and keep the delicate live math precise. And it's why M8.5's QLoRA could freeze a 4-bit base yet train fp16 adapters on top: the frozen part tolerates coarseness, the learning part can't.

The format zoo, decoded

GGUF — the file format of llama.cpp and therefore Ollama and LM Studio: single self-contained file (weights + tokenizer + metadata), CPU-first with GPU offload, quant levels spelled like Q4_K_M (≈4.5 bits/weight, the community's default "sweet spot") or Q8_0 (near-lossless). GPTQ and AWQ — GPU-native 4-bit formats: both use calibration data to quantize cleverly rather than blindly (GPTQ minimizes layer output error; AWQ identifies activation-important weights and protects them), typically served through vLLM. bitsandbytes — the "quantize on load" convenience flag (load_in_4bit=True) from QLoRA, best for experimentation and fine-tuning rather than fast serving. Rule of thumb: laptop/local → GGUF; GPU serving → AWQ/GPTQ; training → bitsandbytes.

Two speed tricks you'll hear named

FlashAttention computes exact attention without ever materializing the full n×n matrix in slow GPU memory — it tiles the computation through fast on-chip SRAM (M7.1's memory hierarchy, paying off). Nothing approximate; just dramatically less memory traffic, which is the actual bottleneck of decode. Speculative decoding: a small "draft" model proposes several tokens cheaply, the big model verifies them in one parallel pass (verification is prefill-shaped, and prefill is cheap per token) — accepted guesses arrive at draft-model speed with big-model quality, typically 2–3× faster generation with mathematically identical output distribution.

Real numbers

Llama-3-8B, the actual downloads: fp16 16.1 GB · Q8_0 GGUF 8.5 GB · Q4_K_M GGUF 4.9 GB — the file Ollama pulls by default, and why ollama run llama3 works on an 8 GB laptop. Measured quality cost of good 4-bit quantization: typically 1–3% on benchmark suites (perplexity rises a few hundredths) — for a 3.3× memory saving and roughly proportionally faster decode, since decode is memory-bandwidth-bound (M11.2): fewer bytes to stream per token = more tokens per second. Below ~3 bits the floor gives way and quality falls off a cliff; 4-bit is the current sweet spot for a reason.

Connect the dots

This is M7.2's bytes-per-parameter table become a lifestyle: params × 0.5 bytes ≈ your GGUF file size (plus block scales). The reason quantized decode is faster, not just smaller, is M11.2's insight that decode streams bytes from VRAM — shrink the bytes, speed the stream. And if you've ever wondered why your local Ollama model feels slightly blunter than the API version of the same model: you're comparing Q4 to fp16 (plus a different sampling config, M11.1). Now you can name the difference instead of vibing it.

ollama run llama3.1:8b-instruct-q4_K_M  "Explain what a KV cache is in 3 sentences."
ollama run llama3.1:8b-instruct-q8_0    "Explain what a KV cache is in 3 sentences."

# watch tokens/sec in the stats line; then compare answer quality
# on 5 prompts of your own (one factual, one code, one reasoning).

# GPU/Python route instead — 4-bit in transformers via bitsandbytes:
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    quantization_config=BitsAndBytesConfig(load_in_4bit=True,
                                           bnb_4bit_quant_type="nf4"))
print(model.get_memory_footprint() / 1e9, "GB")   # ~5.7 vs ~16 fp16

The exercise that matters: on your 5 prompts, can you reliably tell Q4 from Q8? Most people can't without reasoning-heavy tasks — which is exactly the 1–3% benchmark story, experienced firsthand. Note where Q4 does stumble (usually multi-step arithmetic and rare facts).

If you remember one thing

Quantization snaps each weight to a coarser number line — int4 means 16 notches per block, ~4× smaller and correspondingly faster to stream, at a 1–3% quality cost because billions of redundant weights average the rounding noise away. Weights coarsen well, activations don't (outliers), and the formats are just packaging: GGUF for local, GPTQ/AWQ for GPU serving, bitsandbytes for training.

Interview questions

Why does 4-bit quantization barely hurt quality when it deletes 75% of the information?

Three reasons. (1) Redundancy: models are massively overparameterized — training never needed most of that precision (the same fact LoRA exploits: updates are low-rank, weights are compressible). (2) Error averaging: every output is a sum over thousands of weight×activation products (dot products); independent rounding errors partially cancel, so the SUM's relative error is far smaller than any weight's. (3) Block-wise scaling: quantizing in groups of 32–64 with per-block scale factors keeps the 16 notches matched to each block's local range, so no weight is grossly misplaced. The limit: below ~3 bits, errors stop averaging out and quality collapses nonlinearly.

Why are activations harder to quantize than weights?

Weights are static — known offline, so you can pick optimal block scales, reorder, and calibrate (GPTQ/AWQ do exactly this). Activations are computed at runtime and, in transformers, exhibit extreme outlier channels: a handful of dimensions with magnitudes ~100× the median that carry disproportionate signal (LLM.int8() documented this). A naive 4-bit grid either clips outliers (destroying their signal) or stretches to fit them (crushing everything else into two notches). Practical consequence: standard "4-bit models" are weight-only quantization — activations, KV cache, and arithmetic stay fp16 — and weight memory is fortunately the dominant bill.

Someone asks whether to run Q4 or Q8 locally, or pay for an API. Give the engineer's decision tree.

How much VRAM/RAM? 8B model: Q4 ≈ 5 GB, Q8 ≈ 8.5 GB, fp16 ≈ 16 GB — pick the largest that fits with room for KV cache (M11.2). Task type? Chat/summarization/RAG-answering: Q4_K_M is indistinguishable in blind tests — take the speed. Multi-step reasoning, math, code where a 1-3% edge compounds across steps: prefer Q8 or fp16. Privacy or per-token cost dominates → local; peak quality or no hardware → API (which serves fp16/fp8 on H100s). And always benchmark on YOUR 20-prompt golden set (11.4's habit) rather than trusting leaderboard deltas — quantization sensitivity is model- and task-specific.

Explain speculative decoding and why it produces identical output distributions.

A small draft model generates k candidate tokens autoregressively (cheap). The large model then scores all k positions in ONE parallel forward pass — verification is prefill-shaped, and prefill parallelizes (M11.2). Each draft token is accepted with probability min(1, p_large/p_draft) via rejection sampling; on first rejection, the large model's own distribution (corrected) supplies the token, and drafting resumes. The rejection-sampling construction mathematically guarantees the final sequence is distributed exactly as if the large model had sampled alone — it's lossless speedup, typically 2-3× when the draft model agrees often (which it does on easy tokens: articles, syntax, obvious continuations — most of language).

What problem does FlashAttention solve if it computes exactly the same attention?

Memory traffic, not math. Naive attention materializes the n×n score matrix in HBM (GPU main memory), reads/writes it multiple times (scores → softmax → weighted sum), and at long context those transfers dominate runtime — attention is bandwidth-bound, not FLOP-bound. FlashAttention tiles Q, K, V into blocks that fit in on-chip SRAM (~100× faster than HBM), computes softmax incrementally with a running max/denominator (the online-softmax trick), and never writes the full matrix. Same numbers out, 2–4× faster and O(n) memory instead of O(n²) — which is also what made longer training contexts affordable. It's M7.1's memory-hierarchy lesson as a single algorithm.
