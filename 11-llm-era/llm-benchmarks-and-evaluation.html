LLM Benchmarks & Evaluation

"Model X scores 88.7 on MMLU." You've read a hundred sentences like that — time to know what's actually being measured, how the numbers get inflated, and why the leaderboard's winner is routinely the wrong model for your task. This is the measurement thread of the course (M3.6 → perplexity → MTEB → span-F1) arriving at its hardest case: how do you score a model whose output is free text?

The benchmark landscape, decoded

Four families cover most headline numbers. MMLU — 14k multiple-choice questions across 57 subjects (law, medicine, math…); measures broad knowledge; scored by exact letter match. GSM8K / MATH — grade-school and competition math word problems; measures multi-step reasoning; scored by final answer. HumanEval — 164 Python function specs; the model writes code, unit tests execute it; scored pass@k (does any of k samples pass?) — the most honest of the bunch because running code can't be sweet-talked. MT-Bench / Chatbot Arena — open-ended chat quality; no ground truth exists, so either a strong LLM grades responses (MT-Bench) or thousands of humans vote in blind A/B battles feeding an Elo rating (Arena — chess ranking math applied to chatbots, the hardest number to game because the test set is live humans).

Contamination: training on the test

Benchmarks are text on the internet. Pretraining corpora are… the internet (M6.1). When test questions leak into training data — verbatim or paraphrased — the model memorizes answers it appears to reason toward, and a public number quietly inflates. Evidence is everywhere: models scoring suspiciously better on GSM8K's public set than on freshly-written problems of identical difficulty (that's exactly why GSM1k was created — a private clean rewrite showing drops of up to 13 points for some models). Defenses: private held-out sets, contamination scans (n-gram overlap between corpus and benchmark), post-cutoff benchmarks built from new material, and live evals (Arena) whose "test set" is tomorrow's users. Rule: treat any public benchmark number as an upper bound on true capability.

LLM-as-judge: the grader that has biases

For open-ended output there's often no gold answer, and human grading doesn't scale — so we ask a strong LLM to grade. It works surprisingly well (MT-Bench judge agreement with humans ≈ human-human agreement) but the judge has documented, repeatable biases: position bias (prefers whichever answer it read first), verbosity bias (longer ≈ better, even when padding adds nothing), and self-preference (models favor text in their own style, including literally their own outputs). None are fatal; all are correctable-by-design.

The eval that actually matters: yours

Leaderboard rank answers "which model is generally capable?" Your production question is "which model, at which price, handles my distribution of inputs?" — and no public benchmark contains your tone requirements, your domain vocabulary, or your failure costs. The professional habit (you've built it twice: M9.5 for embeddings, span-F1 for NER) is a golden set: 20–100 real cases, each with a rubric of checkable criteria — correctness, groundedness ("no claims beyond the provided context"), format compliance. Score with exact checks where possible, LLM-as-judge (swap-corrected) where not. Run it on every model switch, prompt change, and retrieval tweak — it's a unit test suite for behavior, and it converts arguments about vibes into diffs.

Real numbers

Scale of the standard suites: MMLU ~14k questions (random chance = 25; ~90 is the current frontier); GSM8K 8.5k problems; HumanEval 164 tasks (why its scores are noisy — one task ≈ 0.6 points); Chatbot Arena millions of human votes, where a ~30-point Elo gap ≈ 54% win rate — closer than headlines suggest. MT-Bench's judge agrees with humans ~80% of the time, roughly the human-human rate. And the number that matters most here: a 20-question golden set for your chatbot costs about an afternoon to build and answers questions no leaderboard can.

Connect the dots

This closes the measurement arc that started with M3.6's "accuracy lies": every layer of the stack got its own honest ruler — F1 for classifiers, perplexity for LMs, recall@k/MTEB for embeddings, span-F1 for NER, and now execution tests, Elo, and swap-corrected judges for LLMs. Same discipline every time: define the metric before you argue, distrust averages, hold out a clean test set. Next page's reasoning models were trained on this page's insight — that verifiable rewards (code that runs, math that checks) are the only graders that can't be charmed.

Build: a golden-set eval with a swap-corrected judge
import json, itertools
from openai import OpenAI          # any chat-completions API works
client = OpenAI()

golden = json.load(open("golden.json"))   # 20 items you wrote:
# {"q": "...", "must_contain": ["refund", "14 days"], "context": "..."}

RUBRIC = """Score the ANSWER 1-5 on: (a) factually consistent with CONTEXT
(b) directly answers QUESTION (c) no unsupported claims. Reply as JSON:
{"score": n, "unsupported_claims": [...]}"""

def judge(q, ctx, ans):
    r = client.chat.completions.create(model="gpt-4o", temperature=0,
        messages=[{"role":"user","content":
          f"{RUBRIC}\n\nQUESTION: {q}\nCONTEXT: {ctx}\nANSWER: {ans}"}])
    return json.loads(r.choices[0].message.content)["score"]

scores = []
for item in golden:
    ans = my_bot(item["q"])                      # your pipeline
    hard = all(k.lower() in ans.lower() for k in item["must_contain"])
    scores.append((hard, judge(item["q"], item["context"], ans)))

print(f"hard-checks passed: {sum(h for h,_ in scores)}/{len(scores)}")
print(f"mean judge score:   {sum(s for _,s in scores)/len(scores):.2f}")

Two upgrades that teach the page's lessons firsthand: (1) run the whole eval twice and compare — the variance you see is judge noise, and it's why single-run comparisons under ~5 points of difference are meaningless; (2) for A/B model comparisons, judge each pair in both orders and count only swap-consistent wins. Keep golden.json in git — it's a behavior test suite now.

If you remember one thing

A benchmark measures performance on the benchmark: MMLU = knowledge recall, GSM8K = arithmetic reasoning, HumanEval = executed code, Arena = human preference Elo — and contamination inflates anything public. LLM-as-judge works but carries position, verbosity, and self-preference biases you must design around (swap orders, cap length credit, foreign judge). The eval that decides anything real is a golden set of your own cases, run on every change.

Interview questions

What do MMLU, GSM8K, HumanEval, and Chatbot Arena each actually measure, and which would you trust most?

MMLU: broad knowledge recall in multiple-choice form — 57 subjects, exact letter match; measures stored knowledge and exam skill. GSM8K/MATH: multi-step quantitative reasoning, scored on final answer. HumanEval: functional code generation, scored by executing unit tests (pass@k). Arena: open-ended chat preference via blind human A/B votes aggregated into Elo. Trust ranking for real capability: execution-based (HumanEval-style) and live-human (Arena) age best because neither can be satisfied by memorization alone — code must run, and Arena's "test set" is tomorrow's fresh users. Static public text benchmarks (MMLU, GSM8K) are most contamination-prone and should be read as upper bounds.

What is benchmark contamination, how does it happen, and how do you detect it?

Test items leaking into training corpora — verbatim (benchmark files on GitHub, Q&A sites quoting problems) or paraphrased — so the model memorizes answers rather than deriving them, inflating the public number. Detection: n-gram overlap scans between corpus and benchmark; performance deltas between public sets and privately-rewritten equivalents of matched difficulty (GSM1k found up to ~13-point drops for some models); suspicious verbatim-completion probes (give the question's first half, see if the model completes it word-for-word); and post-training-cutoff benchmarks. Mitigation as a consumer: prefer private/live/execution evals and your own golden set; as a builder: decontaminate training data against known suites.

Name the three classic LLM-as-judge biases and a mitigation for each.

(1) Position bias — the judge favors the answer shown first (or last, model-dependent). Fix: evaluate every pair in both orders; count only swap-consistent verdicts, treat flips as ties. (2) Verbosity bias — longer answers score higher independent of content. Fix: instruct the rubric to penalize padding, normalize/limit lengths, or spot-check length-vs-score correlation. (3) Self-preference — judges rate their own (or same-family) outputs higher. Fix: use a judge from a different model family than any contestant, or a panel of judges. Plus the general mitigations: pointwise rubrics with concrete criteria instead of raw "which is better," temperature 0, and measuring judge-human agreement on a labeled sample before trusting it at scale.

Your team is choosing between two models for a RAG chatbot. Leaderboards put model A 3 MMLU points ahead. What's your evaluation plan?

Ignore the 3 points — wrong task (MMLU is closed-book MCQ; RAG answering is grounded generation) and within contamination/noise range. Plan: (1) build a golden set of 30–50 real user questions with retrieved contexts and reference answers/criteria drawn from production logs; (2) define metrics: groundedness (no claims beyond context), answer correctness against the criteria, format compliance, plus latency and cost per query; (3) hard-check what's checkable (must-contain strings, citation validity), LLM-judge the rest with both-order swaps and a judge from a third family; (4) run each model through the identical pipeline (same retrieval, same prompts, T=0), twice, to see judge variance; (5) decide on quality-per-dollar at your traffic, not abstract rank. Document it so the next model release re-runs in an hour.

Why is pass@k a better metric shape than accuracy for code models, and what's the catch?

pass@k asks: given k sampled attempts, does at least one pass the unit tests? It matches real usage (developers retry / pick from suggestions), rewards models whose samples are diverse enough to cover alternative solutions, and — because scoring is execution-based — is immune to plausible-but-wrong text. Catches: it depends on sampling settings (temperature that maximizes pass@100 hurts pass@1, so published numbers must state k and temperature); tests can be gamed if weak (passing ≠ correct for untested edge cases); small suites (HumanEval = 164 tasks) make single-task noise visible; and training on solutions-in-the-wild contaminates it like any static set — hence fresh-problem suites like LiveCodeBench that only use problems published after the model's cutoff.
