RAG Internals

The final module x-rays the system you started this course already using. You built RAG by wiring libraries together; now you can label every box with the module that explains it — and that labeling is the point. When retrieval fails in production, "it's not finding the right chunks" becomes a precise diagnosis with named fixes, not a shrug. Let's walk the pipeline end to end, then build a complete one in ~80 lines with no vector database at all — to prove you know exactly what the database was doing for you.

The whole pipeline, every box labeled

RAG is two phases. Offline (indexing), once: documents → chunk → embed each chunk (M9's all-MiniLM) → store vectors in an index. Online (query), per question: embed the query with the same model → find nearest chunk vectors by cosine (M1.2) → paste the top chunks into the prompt (M8.3's template) → the LLM answers, grounded (M11.6). Every arrow is something you've now opened: the embedder is a distilled contrastively-trained bi-encoder (M9), "nearest by cosine" is the dot product of normalized vectors (M1.2), and "answer grounded" is the injection-aware, hallucination-managed generation of M11.

Chunking: the decision that quietly caps your quality

Chunking is the most underrated dial in RAG, and it's a genuine trade-off. Too large and a chunk mixes several topics — its single embedding is a muddy average (M9.1's pooling problem at document scale), so it matches everything weakly and nothing strongly, and it wastes context tokens (M11.2) on irrelevant text. Too small and a chunk loses the context that made it meaningful — a sentence saying "it doubled year over year" is useless without knowing what "it" is. Approaches climb a ladder: fixed-size (simplest), token-aware (count in tokens, M5.1, so chunks fit budgets exactly), overlapping windows (carry ~10–20% into the next chunk so a fact split across a boundary survives), and semantic (split on topic shifts using embedding distance — the embedder deciding its own boundaries). Start with ~200–500 token chunks and ~50-token overlap; then, crucially, measure (M9.5, next pages).

Indexing: brute force, then the graph that beats it

With N chunk vectors, finding the query's nearest neighbors is conceptually a loop: compute cosine against all N, sort, take top-k. That's brute-force (flat) search — exact, and completely fine up to ~10k–100k chunks (it's the numpy one-liner in the build). Past that, scanning every vector per query gets slow, so we trade a sliver of accuracy for speed with approximate nearest neighbor (ANN) search — and HNSW is the algorithm your vector DB almost certainly runs.

Metadata filtering and hybrid search: your TF-IDF returns

Two upgrades close the loop to what you already knew. Metadata filtering: store fields alongside each vector (date, author, doc type) and constrain search — "only 2024 chunks," "only from the handbook" — cheap precision the pure-vector purist forgets. Hybrid search: dense vectors capture meaning but miss exact tokens (part numbers, error codes, rare names — the OOV weakness of any embedder); BM25, the modern heir of your TF-IDF, nails exact-term matching. Run both, fuse the rankings (reciprocal rank fusion), and you cover each method's blind spot. Your classical NLP wasn't superseded — it's a production component sitting right beside the neural one.

Real numbers

Scale intuitions: a 10k-chunk corpus at 384-D fp32 is ~15 MB of vectors — brute-force search returns in single-digit milliseconds in numpy, no database needed. HNSW earns its keep past ~1M vectors, where it hits ~95–99% recall at sub-millisecond latency while brute force would take ~100 ms — the accuracy you trade is real but small, and tunable (higher ef_search → more recall, more time). Typical chunking: 256–512 tokens, ~50 overlap; the single most common RAG bug remains chunks so large the real answer is a 5% slice of a muddy embedding.

Connect the dots

This page is the course folding in on itself: M1.2 (cosine) is the search, M5.1 (tokens) sets chunk budgets, M9 (MiniLM) is the embedder, M8.3+M11 are the generation, and your old friend TF-IDF comes back as BM25 in hybrid search. The build below deliberately uses no vector database — once you've written the numpy cosine loop, "vector DB" stops being magic and becomes "brute force plus HNSW plus metadata, productionized." That demystification is the whole module's job.

Build: complete RAG in ~80 lines, no vector DB
import numpy as np, textwrap
from sentence_transformers import SentenceTransformer
from openai import OpenAI

embedder = SentenceTransformer("all-MiniLM-L6-v2")   # M9, yours now
client = OpenAI()

# --- OFFLINE: chunk + embed -------------------------------------
def chunk(text, size=400, overlap=50):               # token-ish by words
    words = text.split()
    step = size - overlap
    return [" ".join(words[i:i+size]) for i in range(0, len(words), step)]

docs = open("handbook.txt").read().split("\n\n---\n\n")   # your corpus
chunks = [c for d in docs for c in chunk(d)]
index = embedder.encode(chunks, normalize_embeddings=True)  # (N, 384)

# --- ONLINE: retrieve + generate --------------------------------
def rag(question, k=4):
    q = embedder.encode([question], normalize_embeddings=True)[0]
    sims = index @ q                                  # cosine = dot (M1.2)
    top = np.argsort(-sims)[:k]                       # brute-force top-k
    context = "\n\n".join(f"[{i}] {chunks[i]}" for i in top)
    prompt = (f"Answer using ONLY these sources; cite [n]. "
              f"If unsupported, say so.\n\n{context}\n\nQ: {question}")
    r = client.chat.completions.create(model="gpt-4o-mini", temperature=0,
        messages=[{"role": "user", "content": prompt}])
    return r.choices[0].message.content, top

print(rag("What is the refund window?"))

That's a real RAG system — the vector DB you'd normally reach for is those two lines (index @ q and argsort) plus HNSW for scale and metadata filters for precision. You'll extend exactly this pipeline in 12.2 (add a reranker) and evaluate it in 12.3. Keep it; it's the spine of the course capstone.

If you remember one thing

RAG is embed-chunks-offline, embed-query-online, cosine-search, stuff-and-generate — and every box is a module you now own; the only real craft is chunking (size vs coherence) and indexing (brute force under ~100k, HNSW beyond). A vector database is brute-force cosine + a small-world graph + metadata, packaged — and your TF-IDF lives on as BM25 in hybrid search.

Interview questions

Walk through a RAG pipeline end to end and name the failure mode at each stage.

Chunk (too large → muddy multi-topic embeddings that match weakly; too small → lost context) → embed chunks (wrong/weak embedder for domain → poor separation, M9.5) → index (ANN recall too low → misses relevant chunks; no metadata → can't scope) → embed query (must be the SAME model and, for asymmetric search, the right instruction prefix, M9.2) → retrieve top-k (k too small → answer chunk not retrieved; k too large → noise + context bloat, M11.2) → assemble prompt (poor ordering → lost-in-the-middle, M11.2; no delimiting → injection, M11.6) → generate (temperature too high → hallucinated citations, M11.1; no grounding instruction → unsupported claims). Debugging rule (12.3): first separate retrieval failure from generation failure — did the right chunk even make it into context?

How do you choose chunk size and overlap, and why does it matter so much?

It sets a ceiling on retrieval quality because a chunk's single embedding must represent all its content (pooling averages meaning, M9.1): oversized chunks blur multiple topics into one vector that ranks mediocre everywhere and burn context tokens; undersized chunks strip the context that disambiguates references. Choose by content structure: prose ~256–512 tokens with ~10–20% overlap so boundary-straddling facts survive in at least one chunk; structured docs (FAQ, code, tables) split on natural units (Q&A pairs, functions) rather than length; token-aware counting (M5.1) to hit budgets exactly. Then measure — recall@k on a labeled query set (M9.5/12.3) — and tune; chunking is empirical, not a fixed rule. Semantic chunking (split on embedding-distance topic shifts) helps on heterogeneous documents.

Explain HNSW intuitively and the accuracy/speed trade it makes. When would you NOT use it?

HNSW builds a multi-layer navigable small-world graph: upper layers are sparse with long-range links (highways), lower layers dense with short links (streets), bottom layer contains everything. A query enters at the top, greedily hops toward the nearest node, descends a layer, repeats — reaching the neighborhood in ~log(N) hops instead of N comparisons. The trade: it's approximate (~95–99% recall depending on ef_search/M construction params), uses extra memory for the graph, and is costlier to build/update. Don't use it when N is small (≤~100k) — brute-force flat search is exact, simpler, and fast enough; when you need guaranteed exact recall; or when the index changes constantly (graph maintenance cost). Rule: start flat, adopt ANN only when brute-force latency actually hurts.

What is hybrid search and when does adding BM25 to dense retrieval actually help?

Hybrid = run dense (embedding) retrieval and sparse lexical retrieval (BM25, the TF-IDF heir) in parallel, then fuse rankings (e.g., reciprocal rank fusion). It helps precisely where dense embeddings are weak: exact-token matches the embedder smooths over — product SKUs, error codes, function names, rare proper nouns, legal citations, out-of-vocabulary/domain jargon the encoder rarely saw. Dense captures paraphrase and meaning ("how do I get my money back" ↔ "refund policy"); sparse captures literal terms ("error E-4021"). Fusing covers both blind spots and is one of the highest-ROI RAG upgrades. It matters less when queries and documents are always natural-language paraphrases with no critical exact tokens.

A colleague says "we need a vector database." When is that true, and what are they actually buying?

For a small corpus (≤~100k chunks) it's often overkill — numpy brute-force cosine over an in-memory matrix is milliseconds and zero ops burden. A dedicated vector DB earns its place at scale or with production needs: ANN indexing (HNSW/IVF) for millions of vectors at low latency, metadata filtering and hybrid search built in, persistence and incremental updates/deletes, sharding/replication, and concurrency. So they're buying an ANN index + metadata engine + operational infrastructure, not a new capability — the retrieval math is the same dot product you can write in one line. Frame the decision by corpus size, update rate, latency SLA, and team ops capacity, not by "everyone uses one."
