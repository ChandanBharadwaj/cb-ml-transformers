Tool Calling & Agents

You've used agentic tools — function calling, ReAct loops, maybe MCP, and coding agents like Cursor or Claude Code. This page demystifies the last black box, and the reveal is the same one that has run through the whole course: it's all just tokens. A model that only predicts the next token (M4.1) can't "call" anything. What actually happens is a beautifully simple illusion built from generation, parsing, and a loop — and once you see it, the course capstone is to build one yourself, from the raw API, over the RAG you already built.

Function calling: constrained generation plus a runtime

Here's the whole trick. You describe your tools as JSON schemas and send them in the prompt (serialized into tokens, like everything else). The model, when it decides a tool is needed, doesn't execute anything — it generates text in the shape of a tool call: a JSON object naming the tool and its arguments. Your code parses that JSON, actually runs the function, and feeds the result back into the conversation as more tokens. The model then continues, now able to attend to the result. "The model called the weather API" really means: the model emitted {"tool":"get_weather","args":{"city":"Paris"}}, your runtime saw it, called the API, and pasted "18°C" back. The model's only superpower is producing well-formed JSON on cue (helped by fine-tuning, M8.3, and constrained decoding); everything else is your loop.

The ReAct loop: an agent is tool-calling in a while-loop

An "agent" sounds like a new kind of thing; it's the above, looped, until the task is done. The pattern is ReAct — Reason, Act, Observe: the model thinks about what to do (chain-of-thought, M11.5), acts by emitting a tool call, your runtime executes and returns an observation, and the loop repeats — each cycle's result feeding the next reasoning step — until the model emits a final answer instead of a tool call. That's it. Multi-step research, "book me a flight," a coding agent editing files: all the same loop, with different tools and more iterations. The model supplies the reasoning and the next action; your code supplies the execution and the memory (the growing transcript).

Where it breaks, and where MCP sits

Honest failure modes, because agents fail in ways single calls don't. Loops: the model repeats a failing action forever (cap iterations, detect repeats). Hallucinated tools or arguments: it invents a function you didn't provide or malformed args (validate against the schema, return errors as observations so it can recover — error recovery is a real skill some models have and some don't). Compounding errors: a wrong step early poisons everything after (short loops, checkpoints, human confirmation on consequential actions — M11.6's least-privilege, now essential). Context growth: every observation is appended, so long tasks fill the window (M11.2) and cost balloons. And MCP (Model Context Protocol) is simply a standard for how tools describe themselves and get called — so a tool written once works with any MCP-speaking agent, instead of every app reinventing its own schema format. It's a USB port for tools, not new intelligence.

How Cursor and Claude Code actually work

No magic, now that you can see the parts: a coding agent is the ReAct loop with file-and-shell tools (read file, edit file, run command, search) plus your codebase as retrievable context (RAG, M12.1 — embed the repo, retrieve relevant files into the prompt). It reasons about your request, reads files to understand them, edits, runs tests, reads the failures as observations, and iterates — exactly the loop above, with a repo for a world. The "agent" is a for-loop around an LLM with good tools, good retrieval, and careful prompting. You have now accounted for every piece.

Real numbers

Practical agent economics: each ReAct step is a full LLM call whose prompt is the entire growing transcript, so a 10-step task can cost far more than 10× a single call — early tokens get re-processed every step (though prompt caching and the KV cache, M11.2, soften prefill cost). Reliability drops with length: if each step succeeds with probability 0.95, a 10-step task completes end-to-end only ~0.95¹⁰ ≈ 60% of the time — which is why short loops, verification, and per-step guards matter more than clever prompts. And why production agents cap iterations (commonly 10–25), validate every tool call against its schema, and gate irreversible actions behind human confirmation.

Connect the dots

This page collapses the last mystery into things you own: tool calls are constrained generation (M4.1, M11.1) plus your loop; the model reads results by attending to appended tokens (M5.3); reasoning between steps is chain-of-thought (M11.5); a coding agent's codebase context is RAG (M12.1); and every safety concern is M11.6's injection and least-privilege story, now with real actions attached. The capstone below has you build an agent over your own from-scratch RAG — closing the entire course loop.

Course capstone: a from-scratch agent over your from-scratch RAG
import json
from openai import OpenAI
client = OpenAI()

# TWO tools: a calculator and the RAG retriever you built in 12.1
def calculator(expr):  return str(eval(expr, {"__builtins__": {}}))
def search_docs(query): return rag(query)[0]        # your 12.1 rag()

TOOLS = {"calculator": calculator, "search_docs": search_docs}
SCHEMAS = [
  {"name": "calculator", "description": "eval a math expression",
   "parameters": {"type": "object", "properties": {"expr": {"type": "string"}}}},
  {"name": "search_docs", "description": "search the knowledge base",
   "parameters": {"type": "object", "properties": {"query": {"type": "string"}}}},
]

def agent(question, max_steps=8):
    messages = [{"role": "user", "content": question}]
    for step in range(max_steps):                    # the ReAct loop
        r = client.chat.completions.create(
            model="gpt-4o", messages=messages,
            tools=[{"type": "function", "function": s} for s in SCHEMAS])
        msg = r.choices[0].message
        messages.append(msg)
        if not msg.tool_calls:                        # final answer → done
            return msg.content
        for call in msg.tool_calls:                   # ACT + OBSERVE
            args = json.loads(call.function.arguments)
            try:
                result = TOOLS[call.function.name](**args)
            except Exception as e:
                result = f"ERROR: {e}"                 # error-as-observation
            messages.append({"role": "tool", "tool_call_id": call.id,
                             "content": result})       # feed back as tokens
    return "hit step limit"                            # loop guard

print(agent("What's our refund window, and what's 14 days in hours?"))

Run it and watch the trace: the model calls search_docs, reads the retrieved policy, calls calculator on "14*24", and composes both into one answer — a genuine multi-tool agent, in ~30 lines, with no framework. You have now built an agent over a RAG system using an embedding model whose attention heads you can draw from memory. That is the entire course, end to end, in your own hands.

If you remember one thing

A model can only generate tokens — so tool calling is the model emitting JSON, your code parsing and executing it, and the result fed back as tokens; an agent is that in a Reason-Act-Observe loop until a final answer. MCP just standardizes the tool interface; Cursor and Claude Code are this loop with file tools and codebase RAG. The intelligence proposes; your runtime disposes — which is exactly why safety and reliability live in the loop, not the prompt.

Interview questions

A model can only predict tokens. So what actually happens when it "calls a tool"?

Nothing executes inside the model. Tool schemas (name, description, argument types) are serialized into the prompt as tokens. When the model determines a tool is needed, it GENERATES a structured output — JSON naming the tool and arguments — using formatting it learned in fine-tuning (and often enforced by constrained decoding so the JSON is valid). The runtime (your code, or the API wrapper) detects this output, parses it, validates against the schema, executes the real function, and appends the result to the conversation as more tokens. On the next forward pass the model attends to that result and continues. So "tool use" = constrained generation + an external parse-execute-feedback loop; the model's contribution is deciding when and emitting well-formed calls, not execution.

Explain the ReAct pattern and what each component contributes.

ReAct = Reason + Act + Observe, looped. Reason: the model produces chain-of-thought (M11.5) about the current state and what to do next — this is where multi-step planning lives and why reasoning quality matters for agents. Act: it emits a tool call (structured generation). Observe: the runtime executes the tool and returns the result as an observation appended to the transcript. The loop repeats — each observation informing the next reasoning step — until the model emits a final answer instead of a tool call. The division of labor: the model supplies reasoning and action selection; the runtime supplies execution, the growing transcript (memory), and loop control (iteration cap, repeat detection). Interleaving reasoning with acting (vs planning everything upfront) lets the agent adapt to what tools actually return.

What are the main failure modes of agents, and how do you mitigate each?

(1) Infinite/repeated loops — cap max iterations, detect repeated actions, break with a fallback. (2) Hallucinated tools or malformed arguments — validate every call against the schema; return errors as observations so the model can self-correct (error recovery). (3) Compounding errors — a wrong early step corrupts the rest; mitigate with short loops, intermediate verification/checkpoints, and by keeping tasks decomposed. (4) Context growth — every observation is appended, inflating cost and hitting the window (M11.2); mitigate with summarization, retrieval of only relevant history, and pruning. (5) Unsafe actions from prompt injection (M11.6) — tool outputs and retrieved content can carry attacker instructions; enforce least-privilege tools, scoped credentials, and human confirmation on irreversible actions. Reliability math (0.95^n) makes short, verified loops the dominant design principle.

What problem does MCP solve, and what does it NOT do?

MCP (Model Context Protocol) standardizes how tools/data-sources describe their capabilities and how agents invoke them — a common interface so a tool implemented once (a database connector, a file server, an API wrapper) works with any MCP-compatible agent, instead of every application inventing its own function-schema format and glue. Think USB for tools: it's about interoperability and reuse. What it does NOT do: it adds no intelligence, no new model capability, and no security by itself — the underlying mechanic is still generate-JSON → parse → execute → feed back, and all the failure modes and safety requirements (validation, least privilege, injection defense) remain the integrator's responsibility. It's plumbing standardization, valuable but not magic.

Explain how a coding agent like Cursor or Claude Code works, in terms of components you've learned.

It's a ReAct loop (M11.5 reasoning + tool calling) equipped with file/shell tools (read file, edit file, run command, grep/search) and codebase context supplied by RAG (M12.1 — the repo is chunked/embedded and relevant files are retrieved into the prompt, since no codebase fits in a context window). The cycle: reason about the request → read relevant files (retrieval + file tool) to build understanding → propose edits (structured generation) → run tests or commands → read the output as observations → iterate until done. Everything is components you now own: generation (M4/M11.1), attention over appended results (M5.3), chain-of-thought planning (M11.5), retrieval (M12.1), and safety/permission scoping (M11.6). The "agent" is a well-engineered for-loop around an LLM with good tools, good retrieval, and careful prompting — no new primitive.
