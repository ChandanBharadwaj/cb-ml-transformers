RAG Evaluation

"The bot gave a wrong answer." Useless as a bug report — because a RAG system can fail in two completely different places, needing opposite fixes. This page gives you the discipline to tell them apart, and the metrics to track each. It's the measurement thread (M3.6 → M9.5 → M11.4) aimed at the system you actually ship, and it turns "the bot feels worse since we changed the prompt" into a number that either moved or didn't.

The first question: retrieval or generation?

Every RAG failure is one of two kinds, and you must separate them before fixing anything. Retrieval failure: the right information never reached the prompt — no chunk in the top-k contained the answer, so the LLM was doomed from the start (fix retrieval: chunking, embedder, reranking, hybrid search — M12.1/12.2). Generation failure: the right chunk was in context and the LLM still got it wrong — misread it, ignored it, or hallucinated past it (fix generation: prompt, model, temperature, grounding — M11). Conflating them wastes weeks; you'll tune prompts while the real problem is a chunk that never got retrieved. The debug move is mechanical: for a failed answer, look at what was retrieved. Answer present in context? Generation problem. Absent? Retrieval problem.

Retrieval metrics: is the answer even reaching the LLM?

These are M9.5's metrics, now measured on the RAG system rather than the bare embedder. Context recall: of the information needed to answer, how much appeared in the retrieved chunks? (The ceiling on everything — if it's low, nothing downstream can save you.) Context precision: of the retrieved chunks, how many were actually relevant? (Low precision means you're burning context tokens and inviting lost-in-the-middle, M11.2, and injection surface, M11.6.) You can compute these two ways: with a labeled set (query → known-relevant chunk IDs, the gold standard) or, when labels are scarce, with an LLM judging whether each retrieved chunk was needed — the RAGAS approach below.

Generation metrics: did it use what it got?

Faithfulness (groundedness) is the one that matters most for trust: is every claim in the answer supported by the retrieved context? This is the direct, measurable counter to hallucination (M11.6) — decompose the answer into individual claims, check each against the chunks, score the fraction supported. An answer can be fluent, confident, and 40% ungrounded; only this metric catches it. Answer relevance: does the answer actually address the question (not a grounded-but-off-topic ramble)? Together they pin the generation half: faithfulness guards against making things up, relevance against dodging the question.

RAGAS and the LLM-judged pipeline

Labeling gold-relevant chunks for every query is expensive, so the practical pattern (popularized by RAGAS) uses an LLM as the grader — exactly M11.4's LLM-as-judge, pointed at your pipeline. For each query it can estimate context recall/precision (was each chunk useful?), faithfulness (is each answer-claim in the context?), and answer relevance — no human labels required for a first read. Carry M11.4's warnings with it: judges have position/verbosity/self-preference biases, so validate the judge against a small human-labeled sample before trusting it, prefer a judge from a different model family than your generator, and treat scores as directional (did this change help?) rather than absolute truth. Even a noisy automated eval beats shipping on vibes.

Real numbers

What a real RAG eval loop looks like: a golden set of 30–100 questions drawn from actual user logs, each with the reference answer and known-relevant chunk IDs (an afternoon to build, M11.4). Track four numbers per change: context recall, context precision, faithfulness, answer relevance. Typical debugging story: bot "accuracy" is 60%; splitting it reveals context recall is 65% (retrieval is the bottleneck, not the LLM), so you add a reranker (M12.2) and recall jumps to 88% — and answer quality follows without touching a single prompt. That's the entire value of separating the metrics: you fixed the right half. Run the suite in CI on every prompt, model, chunking, or retrieval change; regressions under ~5 points are usually judge noise (run twice to confirm, M11.4).

Connect the dots

This is the whole measurement arc landing on your own system: M3.6's precision/ recall become context precision/recall; M9.5's recall@k measures whether the answer chunk was retrieved; M11.4's LLM-as-judge (biases and all) grades faithfulness; M11.6's grounding check is the faithfulness metric, promoted from a safety guardrail to an evaluation number. Same discipline, top to bottom: name the metric, split the failure, hold out a clean set, distrust a single blended score.

Build: evaluate your 12.1/12.2 pipeline, both halves
import json
from openai import OpenAI
client = OpenAI()

golden = json.load(open("golden.json"))
# [{"q": "...", "answer": "...", "relevant_ids": [3, 17]}, ...]

def context_recall(top_ids, relevant_ids):
    return len(set(top_ids) & set(relevant_ids)) / max(1, len(relevant_ids))

def faithfulness(answer, context):          # LLM-judge (M11.4)
    p = (f"List each factual claim in ANSWER. For each, is it supported "
         f"by CONTEXT? Reply JSON {{'supported': n, 'total': n}}.\n\n"
         f"CONTEXT:\n{context}\n\nANSWER:\n{answer}")
    r = client.chat.completions.create(model="gpt-4o", temperature=0,
        messages=[{"role": "user", "content": p}])
    d = json.loads(r.choices[0].message.content)
    return d["supported"] / max(1, d["total"])

rec, faith = [], []
for item in golden:
    top = rerank(item["q"], retrieve(item["q"], 50))   # 12.2 pipeline
    ctx = "\n\n".join(chunks[i] for i in top)
    ans = generate(item["q"], ctx)                      # 12.1 generation
    rec.append(context_recall(top, item["relevant_ids"]))
    faith.append(faithfulness(ans, ctx))

print(f"context recall@5: {sum(rec)/len(rec):.2f}")     # retrieval half
print(f"faithfulness:     {sum(faith)/len(faith):.2f}")  # generation half

Now the diagnostic power is real: if context recall is low, invest in retrieval (reranking, hybrid, chunking); if recall is high but faithfulness is low, the LLM is ignoring good context — fix the prompt, lower temperature, or add the grounding gate (M11.6). Keep golden.json in git and run this on every change — it's your RAG regression suite.

If you remember one thing

A RAG failure is either retrieval (the answer never reached the prompt) or generation (it did and the LLM blew it) — and you must measure them separately: context recall/precision for the first, faithfulness/answer-relevance for the second. A single blended "accuracy" hides which half to fix; splitting it tells you exactly where to spend your next week.

Interview questions

How do you debug a RAG system that gives a wrong answer?

First, localize: inspect the retrieved context for that query. If the needed information is absent from the top-k, it's a retrieval failure — no generation fix can help, so work on chunking, the embedder, reranking (M12.2), hybrid search, or k. If the information IS present and the answer is still wrong, it's a generation failure — the LLM misread, ignored, or hallucinated past it, so work on the prompt (grounding instructions, chunk ordering for lost-in-the-middle), temperature, model choice, or a faithfulness gate. This retrieval-vs-generation split is the single most important RAG debugging skill; skipping it leads to endless prompt-tweaking against what is actually a retrieval bug (or vice versa). Then quantify with separate metrics so the fix is verified, not assumed.

Define context recall, context precision, faithfulness, and answer relevance.

Retrieval side — Context recall: of the information required to answer, what fraction appears in the retrieved chunks (the ceiling on the whole system); Context precision: of the retrieved chunks, what fraction are actually relevant (low precision wastes context budget and adds noise/lost-in-the-middle/injection surface). Generation side — Faithfulness/groundedness: what fraction of the answer's claims are supported by the retrieved context (the direct anti-hallucination metric); Answer relevance: how well the answer addresses the actual question (catches grounded-but-off-topic responses). The pairing is deliberate: recall/precision diagnose whether good context was assembled; faithfulness/relevance diagnose whether the model used it correctly. You want all four, tracked separately.

What is faithfulness/groundedness and how do you measure it without human labels?

Faithfulness = every claim in the generated answer is entailed by the retrieved context; it's the operational, measurable form of "don't hallucinate" (M11.6). Automated measurement (RAGAS-style): use an LLM to decompose the answer into atomic claims, then for each claim judge whether the context supports it, and score the supported fraction. It requires no gold answers — only the context and the produced answer — which is why it scales. Caveats from M11.4: the judge has biases and noise, so validate it against a small human-labeled sample, use a judge from a different family than the generator, run twice to gauge variance, and treat scores as directional. The same mechanism doubles as a runtime guardrail: gate answers whose faithfulness falls below a threshold.

Your RAG bot's answer quality dropped after a prompt change. How do you confirm and localize the regression?

Run the golden-set eval before and after the change (that's why it lives in git and CI). Because the change was to the prompt, expect retrieval metrics (context recall/precision) to be unchanged — verify that; if they moved, something else changed too. Look at generation metrics: a faithfulness or answer-relevance drop confirms the prompt regression and quantifies it. Then compare individual failing cases old-vs-new to see what the new prompt broke (over-terse instructions dropping grounding? a format constraint fighting the answer?). Guard against false alarms: differences under ~5 points can be judge noise, so run the eval twice and check variance (M11.4). This converts "feels worse" into a specific, reproducible number attached to the specific change.

How do you build a golden evaluation set for RAG, and what makes a good one?

Source questions from real user logs (or realistic synthetic ones an LLM generates from your corpus), covering the actual distribution — common queries, edge cases, known failure modes, and out-of-scope questions the bot SHOULD refuse. For each, record: the question, a reference answer or rubric of must-have facts, and the IDs of chunks that genuinely contain the answer (enabling exact context-recall). Size: 30–100 is enough to be directional and cheap to rerun; grow it as you discover new failure classes (every production bug becomes a regression case). Qualities of a good set: representative of real traffic, includes negatives/refusals, has checkable criteria (exact strings + rubric) so scoring isn't purely judge-dependent, and is version-controlled and run in CI on every retrieval/prompt/model change. It's a behavior test suite, not a one-off report.
