GLiNER: NER as Similarity Search

Last page ended at a wall: the classic head's label menu is architecture — frozen at training time, priced in annotation weeks per new type. GLiNER dissolves that wall with one reframe: stop classifying spans into a menu; start matching spans against label descriptions. And here's the spoiler that makes this the perfect final module: the mechanism is your RAG trick. Embed both sides, compare in a shared space. You've been running this architecture in production without knowing it.

The reframe: what if the label were an input?

Classic NER asks: "given this span, which of my K fixed classes is it?" — the types live in the head's output layer as K rows of a weight matrix, learned and immutable. GLiNER asks a different question: "given this span and this entity-type name as text, do they match?" The moment the type becomes an input string instead of an output class, three things follow at once: the label set is unbounded (any string is a candidate type), it's decided at inference time (you typed "medication" into a list — that list is the model's input), and matching needs a similarity score — which is exactly the machinery you've had since M1.2.

One encoder pass, two kinds of output

The elegant part is where the label names go: straight into the input sequence, alongside the sentence, each prefixed by a special [ENT] token. A bidirectional encoder (GLiNER uses DeBERTa, a BERT-family model — M6.2's look-both-ways attention) reads labels and text together in one pass. So the label embedding that comes out isn't a static dictionary vector — it has attended to the sentence, and the sentence's token vectors have attended to the labels. Everything is contextual, in both directions.

Spans × labels: the similarity grid

Now both sides become vectors in one shared space. Every candidate span (contiguous token run up to ~12 tokens wide) gets a representation built from its start-token and end-token vectors pushed through a small FFN (M5.5's per-position "thinking" layer, reused). Every label embedding goes through its own FFN into the same space. Then: score every span against every label with a dot product, squash to 0–1, keep what clears a threshold. That's the entire "classifier."

score(span, type) = σ( FFNspan(hstart ⊕ hend) · FFNtype(qtype) )

In words: glue together the span's first and last token vectors and project them (that's the span's "advertisement"); project the label's vector into the same space (that's the query); dot product measures agreement (M1.2); sigmoid σ turns it into a 0–1 "is this span an entity of this type?" probability. Each span–label pair is judged independently — which is what makes any number of labels possible.

Why does this generalize? (It's contrastive learning again)

A fair objection: the model never saw "brand" in training, so why does its query vector land anywhere sensible? Because GLiNER was trained on tens of thousands of different entity-type strings — not four. Its training set (Pile-NER) was built by having an LLM annotate ~44k web passages with free-form types, yielding roughly 13,000 distinct entity types: "programming language", "chemical compound", "sports team", "mythological figure"… Trained to pull matching span–type pairs together and push mismatches apart (M2.3's physics, M9.3's loss family, third appearance), the model is forced to learn a general mapping from type-descriptions to regions of span-space. A new type name at inference is just a new point in a space that language itself organizes — exactly why your MiniLM can embed a sentence it has never seen.

The limits — where the magic thins

Three honest caveats, all visible from the architecture. (1) Long entities: spans are enumerated up to a width cap (~12 tokens) — a 40-token legal clause title simply has no candidate span. (2) Nested entities: greedy non-overlap decoding picks one span per stretch of text — "University of California, Berkeley" can't yield both the ORG and the two LOCs inside it (flat NER; nested variants exist). (3) Label wording is prompt engineering: the type string IS the query, so "drug" vs "medication" vs "pharmaceutical product" produce different query vectors and measurably different F1. You already know this instinct from RAG: how you phrase the query changes what you retrieve. Budget an hour of label-wording tuning the same way you budget prompt tuning.

Real numbers

GLiNER-medium: a DeBERTa-v3 backbone of roughly 90M parameters (about 200× smaller than a 175B-class LLM). Trained on Pile-NER: ~44k passages, ~13k distinct entity types, annotated by an LLM — the "distill an expensive teacher into a cheap student" move from M9.4, applied to data instead of attention. The paper's headline: averaged across 20 NER benchmarks it never trained on, GLiNER scores ≈60 F1 zero-shot, beating ChatGPT-style extraction (≈40s F1) while running locally in milliseconds. Ceiling check, per last page: a supervised, in-domain BERT still wins on its own turf (CoNLL ≈94 F1) — zero-shot buys breadth, not per-domain SOTA.

Connect the dots

Both loop-closers are now open. all-MiniLM (M9): bi-encoder, contrastive training, embed-and-compare. GLiNER: the same three ideas wearing an NER costume — label strings are the queries, spans are the documents, the similarity grid is your retrieval step, and the threshold is your top-k. When you typed ["person", "medication", "invoice number"], you were writing three search queries against every span of your text. Your two "black-box" tools turned out to be the same tool.

from gliner import GLiNER

model = GLiNER.from_pretrained("urchade/gliner_medium-v2.1")

text = ("Sundar Pichai visited Google India in June and discussed "
        "the Gemini launch and a 500mg dose of paracetamol.")

# types that were NEVER in any training menu — invent your own:
labels = ["person", "company", "medication", "dose", "product launch"]

for e in model.predict_entities(text, labels, threshold=0.5):
    print(f"{e['label']:15s} {e['score']:.2f}  {e['text']}")

If you remember one thing

GLiNER turns NER into similarity search: entity-type names ride into a bidirectional encoder alongside the text, spans and labels become vectors in one shared space, and a span×label dot-product grid — thresholded — is the extractor. New entity type = new string = new column. It's contrastive embed-and-compare, the same architecture as your retriever — which means as of this page, both tools you started this course using as black boxes are now machines you can draw from memory.

Interview questions

How does GLiNER achieve zero-shot NER, mechanically?

It reframes NER from classification to matching. Entity-type names are inserted into the input sequence (each behind an [ENT] token) and encoded together with the text by a bidirectional encoder, producing one contextual embedding per type. Candidate spans (up to a width cap) get representations from their start/end token vectors via an FFN; a span–type score is sigmoid(dot product) in a shared latent space, thresholded. Since types are input strings rather than output classes, any new type is just a new query vector — no head reshaping, no retraining. Generalization comes from contrastive training over ~13k diverse type strings (Pile-NER), forcing a general type-description → span-region mapping.

Compare classic BERT+BIO NER, GLiNER, and LLM-prompt extraction. When do you pick each?

Classic supervised NER: highest in-domain F1 (~94 CoNLL), cheap/fast inference, but a frozen label menu and thousands of dollars of annotation per new type — pick when types are stable and precision is paramount. GLiNER: zero-shot on arbitrary types (~60 F1 average out-of-domain), ~90M params, local, milliseconds — pick for evolving/custom type sets, privacy, cost, or as a strong baseline before annotating anything. LLM extraction: most flexible (can follow complex instructions, normalize, reason), but slowest, priciest, hardest to bound, and often below GLiNER on pure span extraction — pick when extraction needs reasoning or restructuring beyond span-finding. A common production ladder: prototype with GLiNER, harvest its outputs (human-corrected) as training data, graduate to a supervised model for the types that stabilize.

Why is GLiNER sensitive to how you word the entity-type labels, and what do you do about it?

The label string is embedded and used as the query vector — it's the model's entire definition of the type. Synonymous wordings ("drug" vs "medication" vs "pharmaceutical product") land at different points in embedding space and retrieve differently, exactly like paraphrased queries in dense retrieval. Practice: treat labels as prompts — try 3–5 wordings, evaluate span-F1 on a small gold set, prefer wordings close to how the training distribution would describe the type (common nouns over jargon), and consider label descriptions if the variant supports them. This is prompt engineering with a measurable objective.

What are GLiNER's structural limitations?

(1) Span-width cap: candidates are enumerated only up to ~12 tokens, so very long entities are unreachable by construction. (2) Flat decoding: greedy non-overlapping selection can't emit nested entities ("University of California, Berkeley" as ORG containing LOCs). (3) Label-wording sensitivity: the type string is the classifier, so synonym choice moves F1. (4) Span enumeration is O(n × max_width) pairs scored against L labels — fine for sentences, needs chunking for documents. (5) Zero-shot quality trails supervised in-domain models; domain jargon the encoder rarely saw embeds poorly (the M9.5 domain-shift story, again).

"GLiNER is a retrieval system in disguise." Defend or attack this claim.

Defend, with one precision. Shared machinery: two things embedded into one space (type names ↔ queries, spans ↔ documents), trained contrastively (pull matching pairs, push others — the MNR family), scored by dot products, cut by a threshold (≈ top-k). That's a bi-encoder retriever's blueprint. The precision: GLiNER is closer to a cross-encoder hybrid — labels and text attend to each other in ONE joint pass (M9.2's "read together" luxury), affordable because label lists are short, unlike a corpus of a million chunks. So: retrieval's training and scoring, cross-encoder's joint reading — an elegant middle point on the M9.2 trade-off, feasible precisely because the 'corpus' (your label list) is tiny.
