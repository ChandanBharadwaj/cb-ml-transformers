NER as Token Classification

Loop-closer #2 begins. You've used GLiNER — typed entity names like "medication" or "invoice number" into a list and watched it find them with zero training. To appreciate how strange that is, you first need the classic way — the design that ruled NER for two decades — and its ceiling: a fixed menu of entity types, baked in at training time. This page is the classic recipe, its evaluation rules, and exactly why GLiNER's trick (next page) surprised you.

The classic recipe: a label for every token

Classic NER is M8.1's head-transplant, applied per token: take a pretrained encoder (BERT-family — bidirectional context is exactly what entity disambiguation needs, M6.2), and bolt on a classification head that runs at every position: each token's contextual vector → one label from a fixed set. The labels use the BIO scheme: B-TYPE (begins an entity), I-TYPE (inside/continues one), O (outside — plain text).

Evaluation: span-level, exact-match, unforgiving

NER is scored with M3.6's precision/recall/F1 — but on whole spans, not tokens, and with exact-match severity: a predicted entity counts only if its boundaries AND type both match the gold answer perfectly. Predict "Google" where gold says "Google India"? Zero credit — and it double-hurts: a false positive (your wrong span) and a false negative (the missed gold span). This strictness is why NER F1 numbers look modest next to classification accuracies, why partial-credit variants exist (but exact-match remains the standard), and why span boundaries — not types — are where most real systems bleed points.

The ceiling: a fixed menu, priced per change

Now the limitation that defines the whole classic era. The head is one matrix: 384 → (2 × num_types + 1) logits. The label set is architecture — chosen before training, immortalized in the head's shape. Need a new entity type ("medication", "SKU", "clause reference")? The full bill: annotate hundreds to thousands of examples (BIO, by hand, with M8.2's consistency discipline), retrain, re-evaluate, redeploy. Weeks and real money per type. For 20 years this was simply what NER cost — CoNLL's four types (person/org/location/misc) became the universal demo not because the world has four entity types, but because labeled data is that expensive. Which sets up the question GLiNER answers: what if the entity type were an input instead of an output class?

Real numbers

CoNLL-2003 — the benchmark that defined the field: ~22k sentences, 4 entity types, and two decades of progress legible in one column: rule-based systems ~60 F1 → CRF-era ML ~80 → BiLSTM 2016 ~91 → BERT fine-tune 2019 ~92.8 → modern SOTA ≈ 94 (span-level exact-match — human agreement is ~96–97, so the task is nearly saturated). Annotation economics, the real constraint: quality NER labeling runs $0.05–0.30 per entity; a custom 5-type extractor classically costs thousands of dollars of labeling before the first F1 is measured.

Connect the dots

Now your GLiNER experience has its proper contrast: you typed ["person", "medication", "invoice number"] at inference time and got entities — no annotation invoice, no retraining, types you invented on the spot. Against this page's economics, that should now read as genuinely shocking. Also note the quiet M3.6→here→M12 metric thread: span-F1's exact-match strictness is the same discipline as recall@k's binary honesty — you'll measure GLiNER with it in the next build.

Build: run classic NER, meet its menu
from transformers import pipeline

ner = pipeline("token-classification",
               model="dslim/bert-base-NER",          # BERT + BIO head, CoNLL types
               aggregation_strategy="simple")        # re-merges subword pieces!

text = ("Sundar Pichai visited Google India in June and discussed "
        "the Gemini launch and a 500mg dose of paracetamol.")

for e in ner(text):
    print(f"{e['entity_group']:6s} {e['score']:.2f}  {e['word']}")

# note what it CAN'T see: 'Gemini' might get shoehorned into MISC/ORG,
# '500mg'/'paracetamol' are invisible — MEDICATION isn't on the 2003 menu,
# and no prompt can add it. That wall is this page's whole point.

Try texts from your own domain and watch domain entities fall through the four-type menu. The aggregation_strategy flag is the subword re-merging from the animation, productionized. Keep this pipeline handy — next page's build races it head-to-head against GLiNER.

If you remember one thing

Classic NER = encoder + per-token classification head over BIO tags, scored by span-level exact-match F1. It's accurate, mature — and its label menu is frozen into the head's shape, making every new entity type an annotation-and-retraining project. Hold that ceiling firmly; the next page dissolves it with a trick you already know from your own RAG system.

Interview questions

Explain the BIO tagging scheme and why the B- prefix is necessary.

Each token gets B-TYPE (entity begins), I-TYPE (entity continues) or O (outside), turning span extraction into per-token classification. B- disambiguates adjacent same-type entities: "Paris Berlin Rome" as three LOCs needs B-LOC B-LOC (…) — a plain per-type tag would merge neighbors into one span. Variants exist (BILOU/BIOES add Last/Unit tags for slightly richer boundary signal), but BIO is the standard. Bonus point: illegal sequences like O→I-PER need constrained decoding or post-fixing.

Why is NER evaluated with span-level exact-match F1, and what behavior does that create?

The consumer of NER needs complete, correctly-typed spans — "Google" when the entity is "Google India" is operationally wrong (wrong database key, wrong link). So a prediction scores only on exact boundary + type match; partial overlaps count as both a false positive and a false negative. Consequences: scores look low relative to token accuracy, boundary errors dominate the loss of points, and systems invest heavily in boundary detection. It's M3.6's precision/recall made strict — and the same all-or-nothing honesty as recall@k.

How do you handle the subword/label alignment problem in NER fine-tuning?

Labels are word-level; models tokenize to subwords (M5.1) — "Pichai" becomes [Pi, ##chai]. Standard: assign the word's label to its first subtoken and mask the rest from the loss (label −100 in HF); at inference, aggregate subtokens back into words/spans (HF's aggregation_strategy). Alternatives (label all pieces I-…) exist but first-piece is convention. It's a top-3 source of silent bugs in custom NER code — off-by-one alignment quietly corrupts training labels.

A stakeholder wants five new entity types added to your classic NER system. Walk through the real cost.

(1) Annotation: define guidelines (edge cases! nested mentions!), label 500–2000+ examples per type with double-annotation for consistency (M8.2's 80%) — the dominant cost, likely thousands of dollars/weeks. (2) Retrain: new head shape (menu is architecture), full fine-tune, hyperparameter pass. (3) Re-evaluate: span-F1 per type, regression-check the OLD types (the head changed — M8.1 forgetting applies). (4) Redeploy + monitor. Then the pivot a good candidate makes: for many use cases, a zero-shot system (GLiNER-class) or LLM extraction gets 80–90% of the quality at ~zero marginal cost per type — the classic pipeline is now the HIGH-precision option, not the default.
