LoRA, QLoRA & PEFT

M7.2 left a cliffhanger: fine-tuning a 7B costs ~100 GB while running it costs 14. This page is the resolution — the single cleverest idea in applied ML of the 2020s. LoRA lets you adapt a multi-billion-parameter model by training ~0.1% of its size, and QLoRA puts that on a free Colab. Everything here is M1.3 matrix arithmetic; the depth is in understanding why so little suffices.

The insight: weight CHANGES are simple

Full fine-tuning learns ΔW — the difference between adapted and original weights — for every matrix. LoRA's hypothesis, verified empirically: ΔW is low-rank — the change, unlike the knowledge, is simple. Intuition: fine-tuning doesn't rebuild language competence; it steers existing machinery — "attend more to legal terminology," "adopt this response format." Steering adjustments touch a few directions in the representation space, not all 4096. A matrix that only acts in r directions can be written as the product of two thin matrices — and thin matrices are cheap to train.

W_effective = W_frozen + (α/r) · B·A    A: r×d, B: d×r, r ≪ d
In plain words: keep the giant pretrained W untouched; bolt a thin bypass beside it — compress the input to r dims (A), expand back (B) — and add its output to W's. Only A and B train. For d=4096, r=16: the bypass is 131k parameters beside W's 16.8M — 0.8% — and the residual-style "+" (M5.5's trick, again!) means the base behavior is preserved by default.

The knobs, and QLoRA's final squeeze

r (rank): the bypass's width — 8–64 typical; higher = more expressive change, more params; returns diminish fast (r=16 is the workhorse). alpha: scales the bypass's contribution (α/r multiplier; convention: α = 2r). target_modules: which matrices get bypasses — minimal recipes hit attention's W_Q/W_V; modern default is all linear layers including FFN (remember M5.5: that's where ⅔ of capacity lives). Deployment bonus: after training, either merge (W + BA — zero inference overhead, indistinguishable from full FT) or keep adapters separate — one frozen base serving many tasks by hot-swapping ~50 MB adapter files (multi-tenant fine-tuning, an actual product architecture). (The adapter zoo beyond LoRA — prefix tuning, IA³, prompt tuning — solves the same problem with different attachment points; LoRA won on simplicity and the merge trick.)

QLoRA stacks one more idea: since the base is frozen anyway, store it quantized to 4-bit (NF4 format — M11.3 does quantization justice) and keep only the LoRA math in 16-bit. 8B base: 16 GB → ~4.5 GB; total training footprint ~7 GB — a 24 GB card fine-tunes 8B with room to spare; a free Colab T4 handles it. The quality cost is measurably small (the QLoRA paper matched 16-bit fine-tuning on benchmarks). This single stack — 4-bit frozen base + LoRA — is how virtually all hobbyist and most startup fine-tuning happens.

Real numbers

Llama-3-8B with r=16 LoRA on all linear layers: ~42M trainable (0.52%), adapter file ~84 MB (vs 16 GB for a full checkpoint). Memory: full FT ≈ 100+ GB · LoRA ≈ 18 GB · QLoRA ≈ 6–8 GB. Quality, typical instruction-tuning evals: LoRA within ~1–2% of full FT; QLoRA within ~1% of LoRA. Serving: 100 customer-specific adapters on ONE base model = 16 GB + 100×84 MB ≈ 24 GB total, vs 1.6 TB for 100 full copies — the multi-tenant math that makes per-customer fine-tuning a viable business.

Connect the dots

Course threads converging: the bypass is a residual connection (M5.5) at the weight level; freezing is M8.1's dial at its finest setting; B=0 initialization is the identity-default principle (M1.3 → M5.5) yet again; and the memory win is precisely which bars of M7.2's bill vanish. When you see "PEFT" in a library name (HF's peft), "adapters" on a model hub, or fine-tuning-as-a-service pricing that seems impossibly cheap — it's all this page. The M9.5 capstone won't need it (MiniLM is tiny), but the moment you touch an LLM's weights, this is how.

Build (capstone B): QLoRA-tune a small LLM on your own format
# pip install transformers peft trl bitsandbytes datasets
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model
from trl import SFTConfig, SFTTrainer
from datasets import Dataset

name = "Qwen/Qwen2.5-0.5B-Instruct"
bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)   # the Q in QLoRA
model = AutoModelForCausalLM.from_pretrained(name, quantization_config=bnb)
tok = AutoTokenizer.from_pretrained(name)

lora = LoraConfig(r=16, lora_alpha=32, target_modules="all-linear",
                  lora_dropout=0.05, task_type="CAUSAL_LM")
model = get_peft_model(model, lora)
model.print_trainable_parameters()      # ~0.5% — the whole page in one line

# 100 examples of YOUR format — e.g., support tickets → structured triage JSON
rows = [{"messages": [
    {"role": "user", "content": f"Ticket: my invoice #{1000+i} is wrong"},
    {"role": "assistant", "content": '{"category":"billing","urgency":"medium"}'}
]} for i in range(100)]

SFTTrainer(model=model, args=SFTConfig("qlora-demo", num_train_epochs=3,
           per_device_train_batch_size=2, gradient_accumulation_steps=8,
           learning_rate=1e-4, logging_steps=10, report_to=[]),
           train_dataset=Dataset.from_list(rows),
           processing_class=tok).train()

model.save_pretrained("my-adapter")      # ~10 MB file = your entire fine-tune

Compare generations before/after on your format — 100 examples visibly locks in the JSON structure (SFT teaching format, M8.3's lesson, via LoRA's mechanism). Then look at my-adapter/: a few megabytes that steer half a billion parameters. Swap in real tickets from your world and this demo is a shippable pattern.

If you remember one thing

LoRA: freeze W, train a thin low-rank bypass B·A added residual-style — because fine-tuning's changes are simple even when the model isn't. ~0.5% trainable, ~1% quality cost, adapters merge to zero overhead or hot-swap for multi-tenancy. QLoRA: 4-bit frozen base under the same trick → 8B fine-tuning on a free GPU. The pretrain/adapt economy's last-mile technology — and it's all matrices you already understand.

Interview questions

Explain LoRA from first principles — why does low rank suffice?

LoRA freezes pretrained W and learns an additive update ΔW = (α/r)BA with A (r×d) down-projecting and B (d×r) up-projecting, r ≪ d; only A,B train. It suffices because fine-tuning's weight CHANGES are empirically low-rank: adaptation steers existing features (formats, domain emphasis, style) rather than building new competence, so the update acts in few directions of representation space. Aghajanyan et al.'s intrinsic-dimension work and LoRA's own ablations back this: task adaptation lives in a tiny subspace of parameter space.

Where do LoRA's memory savings actually come from? Be precise against the training-memory bill.

From the trainable-parameter-proportional terms (M7.2): gradients, Adam's two moments, and fp32 masters exist only for A,B (~0.5% of params) — collapsing ~70 GB of an 8B's training state to under 1 GB. NOT from weights (base still loaded — 16 GB fp16, unless quantized: QLoRA's 4-bit → ~4.5 GB) and NOT much from activations (forward pass unchanged — still batch/seq-dependent; checkpointing still applies). Full FT ~100 GB → LoRA ~18 → QLoRA ~7: each step names which bill-line it deleted.

Why is B initialized to zero, and what does merging adapters mean?

B=0 makes BA=0 at start: the adapted model is exactly the base on day one — training departs smoothly from known-good behavior instead of from noise (the identity-default principle behind residuals). Merging: after training, compute W' = W + (α/r)BA once and save W' — inference then has literally zero LoRA overhead (no extra matmuls), indistinguishable from a full fine-tune. Alternative: keep adapters unmerged and hot-swap per request — the multi-tenant serving pattern (one base, N ~50 MB adapters).

How do you choose r, alpha, and target modules in practice?

Start r=16, α=32 (the α=2r convention), target all-linear (attention + FFN — FFN holds ⅔ of capacity, M5.5; QLoRA's paper found all-linear matters more than large r). Raise r (32–64) for aggressive behavior change or larger datasets; drop to 8 for tiny data or style-only tweaks. Diminishing returns above r=64 are well-documented. Then treat it like M8.2: LR ~1e-4 (adapters tolerate higher than full FT), watch curves, 3 seeds before believing differences — LoRA changes the parameterization, not the discipline.

When is full fine-tuning still worth it over LoRA?

When the required change is large and deep: continued pretraining on a new domain/language (millions of documents — the update ISN'T low-rank), major capability additions, small models where full FT is cheap anyway (MiniLM-class — M9.5 just fine-tunes everything), or squeezing the last 1–2% on a high-value task with ample compute. Also when serving infrastructure prefers a single merged artifact anyway — though merged LoRA gives that too. Default in 2025 practice: LoRA/QLoRA first; escalate only with evidence the low-rank ceiling is binding (train loss floors early despite data/LR sweeps).
