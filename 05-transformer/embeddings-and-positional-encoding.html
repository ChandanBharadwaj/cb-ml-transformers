Embeddings & Positional Encoding

Token IDs are just index numbers — ID 4937 means nothing by itself. Before attention can work, each ID becomes a vector (old friend: the embedding table), and then something subtle must happen: order has to be injected, because attention — you'll see why — is natively blind to it. This page covers both moves, plus the modern position trick (RoPE) that made 128k-token contexts possible.

The embedding table: word2vec's ghost in every transformer

Step one is a lookup: a matrix of shape vocab × d (MiniLM: 30,522 × 384), where row i is token i's starting vector. Structurally identical to word2vec's V matrix (M2.2) — but with two upgrades: it's trained jointly with the whole network for the end task, and its outputs are only the starting point — static, context-free vectors that the attention layers above will transform into contextual ones (fixing M2.4's bank problem is literally the job of the rest of this module).

The problem: attention is a bag, not a sequence

Here's the subtlety. Attention (M4.4) scores pairs of vectors with dot products and blends by weight. Nothing in that arithmetic knows where a vector sat in the sentence — shuffle the inputs and you get the same scores, the same blends, shuffled. Without help, a transformer sees word soup:

Stamp #1: sinusoidal waves (the 2017 original)

The original transformer added a position vector to each token embedding: position p's vector is built from sines and cosines of p at many frequencies — dimension pairs oscillating fast, medium, slow. Think of it as a binary-counter made smooth: fast dimensions distinguish neighbors; slow ones distinguish sentence regions; together, every position gets a unique, consistent fingerprint — and (the elegant part) the pattern for position p+k relates to p by a fixed rotation, so relative offsets are learnable. No parameters, works for any length.

Stamp #2 and #3: learned positions, then RoPE

Learned positions (BERT, MiniLM, GPT-2): skip the trigonometry — make a second embedding table, one trainable row per position, and add row p to every token at position p. Simpler, works slightly better in-range, but has a hard edge: only as many rows as you trained (512 for BERT/MiniLM, 1024 for GPT-2). Position 513 does not exist. That's the literal origin of your chunker's 512-token limit.

RoPE — rotary position embedding (Llama, Qwen, most modern LLMs) moves position out of the token vector entirely: instead of adding a stamp, it rotates each query and key vector by an angle proportional to its position (at many frequencies, like the sinusoids). The beautiful consequence comes from dot-product geometry (M1.2): rotating both vectors makes their dot product depend only on the angle difference — i.e., attention scores depend on relative distance between tokens, not absolute slots. "Three tokens apart" behaves identically at position 10 and position 10,000. That relative-ness is what lets context windows stretch (with frequency rescaling tricks) to 128k+ — the full story lands in M11.2.

Real numbers

MiniLM's config: "max_position_embeddings": 512 — a learned 512 × 384 table (196,608 parameters), and the reason your RAG chunks cap at 512 tokens: row 513 was never created. GPT-2: 1024 learned positions. Llama-3 with RoPE: zero position parameters, trained at 8k and extended to 128k via rotation-frequency rescaling. Also countable now: MiniLM's full input layer = token table (11.72M) + position table (0.20M) + segment table (0.0008M) ≈ 11.9M parameters — 52% of the entire model, spent before any attention runs.

Connect the dots

Three mysteries from your production life, closed: (1) the 512-token truncation warning from sentence-transformers = the position table's last row; (2) "context window: 128k" in a model card = how far its position scheme (usually RoPE) was trained/extended to reach; (3) models degrading on very long inputs despite big windows = positions those rotation frequencies rarely saw in training (M11.2's "lost in the middle"). One design choice — how to stamp order — surfaces in your API errors, your chunker config, and your model choice.

Build: see the fingerprints and the 512 wall
import numpy as np
import matplotlib.pyplot as plt

def sinusoidal(n_pos, d):
    P = np.zeros((n_pos, d))
    pos = np.arange(n_pos)[:, None]
    i = np.arange(0, d, 2)[None, :]
    angle = pos / (10000 ** (i / d))
    P[:, 0::2], P[:, 1::2] = np.sin(angle), np.cos(angle)
    return P

P = sinusoidal(100, 128)
plt.figure(figsize=(9, 4))
plt.imshow(P, aspect="auto", cmap="RdBu")     # the famous stripe plot
plt.xlabel("embedding dimension"); plt.ylabel("position")
plt.title("every row = one position's unique fingerprint")
plt.colorbar(); plt.show()

# and the 512 wall, live:
from transformers import AutoTokenizer, AutoModel
tok = AutoTokenizer.from_pretrained("sentence-transformers/all-MiniLM-L6-v2")
print(tok.model_max_length)                    # → 512. Now you know exactly why.

In the stripe plot, notice fast stripes on the left dimensions, slow on the right — the animation's waves as an image. Every position's row is unique; nearby rows are similar. That's all "positional encoding" ever was.

If you remember one thing

Input to a transformer = embedding-table lookup + position stamp. The stamp exists because attention's math is order-blind; the three stamp designs — sinusoidal waves (parameter-free), learned rows (simple, hard length limit — your 512), and RoPE rotations (relative distances, long-context capable) — explain every context-length number you've ever read in a model card.

Interview questions

Why do transformers need positional encoding when RNNs didn't?

RNNs consume tokens sequentially — order is implicit in processing time. Attention processes all positions simultaneously via dot products that are permutation-invariant: shuffle the inputs and outputs shuffle identically, so "dog bites man" ≡ "man bites dog". Position must therefore be injected into the representations themselves (added stamps or rotations) before attention can distinguish orderings.

Compare sinusoidal, learned, and rotary (RoPE) positional encodings.

Sinusoidal: fixed multi-frequency wave fingerprints added to embeddings — parameter-free, defined for any length, relative offsets expressible via rotations. Learned: a trainable per-position table added to embeddings — flexible, slightly better in-distribution, but hard-capped at trained length (BERT/MiniLM's 512). RoPE: rotate Q and K by position-proportional angles so attention scores depend only on relative distance — no added parameters, best extrapolation, and the basis of modern long-context scaling; now the de-facto standard in LLMs.

Why does RoPE make attention depend on relative rather than absolute position?

A dot product between two vectors rotated by angles θ_m and θ_n depends only on the difference θ_m − θ_n (rotations preserve dot products up to the relative angle). Since RoPE sets each token's rotation proportional to its index, q·k becomes a function of (m − n) — the token gap — not of m and n individually. Linguistically that's the right prior: "adjective two tokens before its noun" shouldn't care whether it happens at position 5 or 5,000.

The embedding table is over half of MiniLM's parameters. Is that typical? What changes at LLM scale?

Typical for small models: vocab × d (30k × 384) is fixed-ish while layers are thin. At LLM scale the ratio inverts — Llama-3-8B's table is 128k × 4096 ≈ 0.5B, only ~6% of 8B, because layer parameters grow with d² and depth while the table grows with d. Corollaries: small models are "mostly dictionary" (why distillation targets layers, M9.4), and vocabulary choices materially affect small-model size. Many models also tie input/output embedding matrices to save the duplicate.

Can you run a 512-position model on a 2,000-token document? What actually happens?

Not directly: with learned positions there's no row 513 — the library truncates (silently or with a warning) or errors. Workarounds: chunk the document (what RAG pipelines do — with overlap so boundaries don't cut context), use a long-context model, or (research-grade) extend positions by interpolation plus fine-tuning. The practical answer interviewers want: know your model's limit, chunk deliberately, and understand truncation is data loss, not compression.
