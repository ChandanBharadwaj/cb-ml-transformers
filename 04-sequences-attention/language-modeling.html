Language Modeling & Perplexity

Before building the transformer, meet the task it was built for. It sounds almost insultingly simple: given some words, predict the next one. Hold that thought against everything your chatbot does — answers questions, writes code, apologizes, refuses — because all of it, every capability you've shipped on top of an LLM, is this one task, executed in a loop. This page makes that claim precise, and gives you the field's original metric (perplexity) as a bonus.

The task: P(next word | words so far)

A language model is a probability machine: feed it a prefix, it returns a probability for every word in the vocabulary being next. That's the whole contract. "The capital of France is ___" → Paris 0.95. But the same contract, applied to less obvious prefixes, quietly requires everything:

Whole sentences: the chain rule of probability

P(sentence) = P(w₁) · P(w₂|w₁) · P(w₃|w₁w₂) · …
In plain words: the probability of a whole sentence is the product of each word's probability given everything before it. So a next-word machine automatically prices entire texts — and can generate them, one conditional at a time. Generation and probability-scoring are the same machinery viewed twice.

This factorization is why LLMs generate left to right, one token at a time — each new token is a fresh draw from P(next | everything so far), then gets appended to the context for the next draw. It's also why they train so well: every position in every sentence of the internet is a labeled example (the label is simply the next word) — self-supervision (M2.2's trick) at maximum scale.

Perplexity: the original benchmark

How do you score a language model? Cross-entropy (M3.2) per token, averaged. But the field prefers to report its exponential, which has a beautiful reading:

perplexity = e^(average cross-entropy per token)
In plain words: the effective number of words the model is hesitating between at each step. Perplexity 1 = clairvoyant. Perplexity 7 = "as unsure as choosing among 7 equally-likely words." Perplexity 50,000 on a 50k vocabulary = knows nothing. Lower is better, and every LLM headline loss number converts directly: perplexity = e^loss.
Real numbers

GPT-2 (2019) reached perplexity ≈ 29 on the WikiText-103 benchmark; earlier LSTM-era models sat around 40–60; modern LLMs score single digits on comparable text. And a human calibration: people asked to guess next words behave like a model with perplexity roughly 10–15 on typical prose — frontier LLMs are now superhuman at this specific game, which is exactly why their text feels fluent. (Fluent ≠ true — that gap is M11.6.)

Connect the dots

Every product behavior you've built on LLMs is this page wearing a costume: chat = predict next tokens after a transcript that ends with "Assistant:"; code completion in Cursor = next tokens after your cursor; your RAG answers = next tokens after retrieved chunks + question; even tool calling (M12.4) = next tokens that happen to be JSON. There is no second mechanism. One task, worn four ways — and when the streaming cursor blinks in your chatbot UI, that's the chain rule factorization, live.

Build: watch a real LM hesitate
# pip install transformers torch
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

tok = AutoTokenizer.from_pretrained("gpt2")
lm  = AutoModelForCausalLM.from_pretrained("gpt2")

def peek(prefix, k=6):
    ids = tok(prefix, return_tensors="pt").input_ids
    with torch.no_grad():
        logits = lm(ids).logits[0, -1]          # scores for the NEXT token
    probs = torch.softmax(logits, dim=-1)       # M3.2, live
    top = torch.topk(probs, k)
    print(f"\n{prefix!r}")
    for p, i in zip(top.values, top.indices):
        print(f"  {tok.decode(i)!r:>14}  {p:.3f}")

peek("The capital of France is")
peek("She opened the door and")
peek("18 + 24 =")                # watch 2019-era GPT-2 struggle with arithmetic!

Three prefixes, three shapes of hesitation — sharp for facts, wide for open prose, and confused for arithmetic (GPT-2 predates the scale where arithmetic emerges, M7.4 tells that story). You're inspecting the raw probability machine your whole stack is built on.

If you remember one thing

A language model does exactly one thing: assign probabilities to the next token. Sentences follow by the chain rule; generation is repeated sampling; training data is free at internet scale; and perplexity — e^loss — reads as "how many words is it torn between." Everything an LLM appears to do is this task, compounded.

Interview questions

What is a language model, strictly speaking?

A model of the probability distribution over token sequences, almost always factorized autoregressively: P(w₁…wₙ) = Π P(wᵢ | w₁…wᵢ₋₁). It's trained to predict each next token given its prefix. Everything else — chat, code generation, summarization — is this distribution being sampled under different prompts.

Define perplexity and interpret a value of 20.

Perplexity = exp(average per-token cross-entropy) — the geometric-mean inverse probability of the data. Value 20 means the model is, on average, as uncertain as if choosing uniformly among 20 candidate tokens per position. Lower is better; it's dataset-dependent (compare models only on the same text with the same tokenizer — a subtle but classic gotcha, since a different tokenizer changes what "per token" means).

Why is next-token prediction such an effective pretraining task?

Three compounding reasons: labels are free (the next token IS the label — self-supervision at web scale); the task is dense (every token of every document is a training example); and it's a "universal demand" — predicting well across all text requires grammar, facts, style, and reasoning, so loss minimization forces broad competence into the weights. It converts unlimited raw text into unlimited supervised signal.

Is an LLM "just autocomplete"? Give the sophisticated version of both sides.

Mechanically yes: it emits next-token distributions, nothing else. But the dismissive reading fails because doing that task at very low loss provably requires internal computation — world knowledge, in-context pattern induction, multi-step composition — and instruction tuning (M8.3) shapes the distribution toward helpful continuations. The honest framing: the interface is autocomplete; the capabilities needed to do it well are not trivial. Interviewers use this to test whether you can hold both truths.

Why do LLMs generate token-by-token instead of emitting a whole answer at once?

The autoregressive factorization: each token's distribution is conditioned on all previous tokens, including just-generated ones — so token t must exist before token t+1 can be predicted. This is why APIs stream, why long outputs cost proportionally more, and why latency splits into prompt-processing vs per-token generation (mechanics in M5.7, economics in M7.5).
