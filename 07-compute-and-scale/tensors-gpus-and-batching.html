Tensors, GPUs & Batching

New module: the physical layer. You asked for the compute story, and it starts here — what shape data actually takes inside a transformer, why one specific chip architecture eats this workload alive, and why "batch it" is the answer to half of all performance questions. This module is what makes M11's serving tricks and M8's fine-tuning constraints feel obvious instead of arbitrary.

Tensors: the shapes that flow

A tensor is just an n-dimensional array — vector (1-D), matrix (2-D), and up. Everything in a transformer is tensors flowing through matrix multiplies, and one shape matters above all: the activation tensor (batch, sequence, hidden) — B sentences × n tokens × d dims. Follow it through MiniLM for a batch of 32 texts, 128 tokens each: embeddings produce (32, 128, 384); every block maps (32, 128, 384) → (32, 128, 384) (M5.6's closure!); attention internally blooms a (32, 12, 128, 128) score tensor (batch, heads, n, n — the O(n²) made visible); the FFN briefly widens to (32, 128, 1536). Being able to narrate these shapes is what "understands the forward pass" means in practice — and it's how you'll debug every shape-mismatch error for the rest of your career.

Why GPUs: 10,000 line cooks

A CPU is ~8–64 sophisticated cores — brilliant at branching logic, wasted on repetitive arithmetic. A GPU is tens of thousands of simple cores that all execute the same instruction on different data. A matrix multiply is exactly that: millions of independent multiply-adds with zero branching — M1.3's "each output = one dot product" means every output cell can be computed by a different core, simultaneously. Transformers are ~99% matmul by FLOPs; the marriage was arranged in heaven. (.to("cuda") in PyTorch = "copy these tensors to GPU memory and run kernels there"; CUDA is NVIDIA's programming layer for it.)

Batching: keep the stadium full

Here's the operational insight that follows: a GPU processing ONE sentence uses a sliver of its cores — the rest idle. Stack 64 sentences into one (64, n, d) tensor and the same pass fills the hardware; total time barely moves. Latency per batch ≈ flat (until saturation), so throughput ≈ linear in batch size. That's why every inference framework batches (your model.encode(list) call, DataLoaders in training, vLLM's continuous batching for LLM serving — M7.5), and why "GPU utilization: 8%" in nvidia-smi usually means "your batches are too small," not "you need a bigger GPU."

The memory hierarchy sets the limits: VRAM (GPU's own memory, 16–80GB — everything computed must live here), RAM (CPU side, connected by a comparatively slow PCIe pipe), disk. Two practical corollaries: batch size is capped by VRAM (activations scale with batch — next page's math), and shuttling data CPU↔GPU mid-computation is a classic silent performance killer (why preprocessing pipelines and pin_memory exist).

Real numbers

Hardware you'll see quoted, calibrated: consumer RTX 4090 — 24GB VRAM, ~80 fp16 TFLOPs. Cloud T4 (free Colab) — 16GB, ~65. A100 — 40/80GB, ~312. H100 — 80GB, ~1000 with fp8. Batching effect measured on MiniLM (T4): batch 1 → ~90 sentences/s; batch 32 → ~1,800/s; batch 256 → ~2,600/s (saturation). Same model, same chip, 29× throughput — free, from tensor shape alone.

Connect the dots

You've lived this page without the vocabulary: embedding your RAG corpus one-document-at-a-time in a loop vs passing the whole list to encode() — the 20× speedup you may have stumbled into was batching filling the stadium. GPU-poor? MiniLM's 22M params run fine on CPU precisely because it's small (M6.5's "representation is cheap") — but the moment you embed millions of documents, this page is your capacity plan. And the (batch, heads, n, n) attention tensor you met above is the exact object the KV cache (M11.2) exists to avoid recomputing.

Build: measure the batching curve yourself
import time
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")   # add device="cuda" if you have one
texts = ["The quick brown fox jumps over the lazy dog."] * 2048

for bs in [1, 8, 32, 128, 512]:
    t0 = time.perf_counter()
    model.encode(texts, batch_size=bs, show_progress_bar=False)
    dt = time.perf_counter() - t0
    print(f"batch {bs:4d}: {len(texts)/dt:7.0f} sentences/sec")

Plot sentences/sec vs batch size mentally: steep rise, then plateau — the stadium filling, then full. Find where YOUR hardware saturates; that number is your default batch size for every embedding job from now on. (On CPU the curve is flatter but real — vector instructions batch too.)

If you remember one thing

Transformers are tensors — (batch, seq, hidden) — flowing through matmuls; GPUs win because matmuls decompose into thousands of identical independent operations; and batching is how you keep the cores fed: near-flat latency, near-linear throughput, capped by VRAM. Half of all "make it faster" answers in this field reduce to "bigger batches, fewer CPU↔GPU trips."

Interview questions

Why are GPUs so much faster than CPUs for deep learning?

Deep learning is dominated by matrix multiplication — millions of independent, identical multiply-add operations with no branching. GPUs provide thousands of simple cores executing the same instruction on different data (plus high-bandwidth memory and, on modern chips, dedicated matmul units — tensor cores), matching the workload's structure exactly. CPUs' few sophisticated cores optimize for branching and latency, which matmuls don't need. It's workload-shape alignment, not raw superiority — CPUs still win at irregular logic.

Walk the activation shapes through one transformer layer for batch 32, seq 128, d 384, 12 heads.

Input (32,128,384). Q/K/V projections keep (32,128,384), reshaped per head to (32,12,128,32). Scores QKᵀ: (32,12,128,128) — the O(n²) object. Softmax same shape; ×V back to (32,12,128,32); concat + W_O → (32,128,384). FFN: → (32,128,1536) → GELU → (32,128,384). Residuals preserve shape throughout. Fluent shape-narration is a strong systems-competence signal.

Why does increasing batch size raise throughput without (initially) raising latency?

Small batches leave most GPU cores idle — the pass takes roughly the kernel-launch + memory-traffic floor regardless. Growing the batch assigns more independent output cells to idle cores; wall-time per pass stays near-flat until cores/bandwidth saturate, so items-per-second scales ~linearly. Past saturation, latency grows linearly and throughput plateaus. Limits: VRAM (activations scale with batch) and, for user-facing serving, the latency SLO — hence dynamic/continuous batching systems that balance both (M7.5).

Your GPU shows 10% utilization during training. Diagnose.

The GPU is starving, not weak. Checklist: (1) batch too small — grow it or use gradient accumulation; (2) data pipeline bottleneck — CPU preprocessing/dataloading can't keep up (more workers, pre-tokenize, pin memory); (3) excessive CPU↔GPU transfers or synchronizations (item-by-item .cpu() calls, printing tensors in the loop); (4) tiny model where kernel-launch overhead dominates — fuse ops or batch harder; (5) I/O — slow disk/network reads. Order matters: measure the dataloader first; it's the culprit most often.

When is CPU inference the right choice?

When the model is small relative to traffic: MiniLM-class encoders (~22M params) embed hundreds of sentences/sec on CPU — often enough, at zero GPU cost and simpler ops; same for small classifiers and rerankers at modest QPS. Also: strict data-locality environments, edge deployment, and quantized 7B-class LLMs for low-volume internal tools (M11.3's llama.cpp world). The engineering answer is arithmetic: required throughput × model FLOPs vs hardware cost — not reflexive GPU-by-default.
