Training at Scale

Last page ended with a model that can't fit on one GPU. This page is the toolkit that trains it anyway — the four memory tricks you'll actually use on single machines, and the three parallelism strategies (in intuitions, not frameworks) that let 16,000 GPUs act as one. None of it is exotic once you see each trick as an answer to "which bar of the memory bill are we dodging?"

The single-GPU survival kit

Mixed precision: do the heavy math in bf16 (2 bytes, huge speedup on tensor cores), keep an fp32 master copy of weights for stable accumulation of tiny updates — the +28 GB bar from last page, purchased deliberately because bf16 matmuls are 2–4× faster. (bf16 vs fp16 detail worth knowing: bf16 keeps fp32's exponent range, so no loss-scaling gymnastics — it's why everyone switched.) Gradient accumulation: can only fit batch 4, but want batch 64's smooth gradients (M3.3)? Run 16 micro-batches, summing gradients, step once — identical math to big-batch training, paid in time instead of memory. Gradient checkpointing: don't cache every activation; recompute them during backward — ~30% more compute, activations bar shrinks dramatically. These three are checkboxes in every HF Trainer config; now they're decisions instead of incantations.

Beyond one GPU: three ways to split the work

Frontier training composes all three — "3D parallelism": tensor-parallel inside a node (8 GPUs, NVLink), pipeline across nodes, data-parallel across the whole fleet, plus the single-GPU kit everywhere. You will likely never configure this by hand (FSDP/DeepSpeed/Megatron do), but knowing the three axes makes every infrastructure conversation and paper legible.

What a real training run looks like

Not a smooth loss curve — a campaign: checkpoints written every few hours (a 70B checkpoint is ~1 TB with optimizer state — even saving is engineering); loss spikes where training destabilizes (responses: skip the bad batch, restore checkpoint, sometimes lower LR); hardware failures as routine (at 16,000 GPUs, several fail daily — automated detect-restart-resume is core infrastructure); and a data curriculum (mixture ratios sometimes shifted late in training — more code/high-quality text near the end). The published "loss curve" is the cleaned-up autobiography of months of firefighting.

Real numbers

Llama-3.1-405B's disclosed campaign: ~16,000 H100s, 54 days for the main run, with a published finding that hardware failures caused ~466 job interruptions — one every ~3 hours, 78% from GPU/HBM faults. Compute ≈ 3.8×10²⁵ FLOPs; power draw of the fleet ≈ a small town. Meanwhile your side of the economy: QLoRA fine-tuning 8B on one 24 GB card uses every single-GPU trick on this page — mixed precision, accumulation, checkpointing — via three lines of Trainer config. Same physics, twelve orders of magnitude apart.

Connect the dots

Config archaeology you can now perform: bf16=True (mixed precision), gradient_accumulation_steps=8 (big-batch math on small VRAM), gradient_checkpointing=True (the activations bar, traded for compute) — the three checkboxes in every fine-tuning tutorial you've ever skimmed are this page's survival kit. And when M9.5 has you fine-tune MiniLM, note the luxury: at 22M parameters, none of this is needed. Model size decides which chapter of this page applies to you.

Build: gradient accumulation, proven identical
import torch, torch.nn as nn

torch.manual_seed(0)
model_a = nn.Linear(10, 1)
model_b = nn.Linear(10, 1)
model_b.load_state_dict(model_a.state_dict())      # identical twins
X, y = torch.randn(64, 10), torch.randn(64, 1)
loss_fn = nn.MSELoss()

# A: one big batch of 64
loss_fn(model_a(X), y).backward()

# B: 8 micro-batches of 8, gradients accumulating
for i in range(8):
    xb, yb = X[i*8:(i+1)*8], y[i*8:(i+1)*8]
    (loss_fn(model_b(xb), yb) / 8).backward()       # note the /8 — mean of means

print(torch.allclose(model_a.weight.grad, model_b.weight.grad, atol=1e-6))  # True

True: eight small backward passes, summed, equal one big one — because gradients are averages and averages decompose (that's also why data parallelism works: the gradient all-reduce across GPUs is this same identity, distributed). One assert, two of this page's tricks demystified.

If you remember one thing

Single GPU: mixed precision + gradient accumulation + checkpointing — speed, effective batch, and memory, each traded consciously. Many GPUs: data parallel (copy model, split batch), tensor parallel (split matrices, needs fast links), pipeline parallel (split layers, assembly line) — composed as 3D at the frontier. And real training runs are campaigns with checkpoints, spikes and daily hardware funerals, not smooth curves.

Interview questions

Explain the three parallelism strategies and when each applies.

Data parallel: replicate the model, split the batch, all-reduce gradients — default whenever the model fits per-GPU; ZeRO/FSDP extend it by sharding optimizer state/gradients/weights across replicas. Tensor parallel: shard individual weight matrices; every matmul becomes a collective operation — needed when layers themselves don't fit, viable only over NVLink-class interconnects (within a node). Pipeline parallel: assign contiguous layer ranges to GPUs, stream micro-batches to fill the assembly line — spans nodes where links are slower; costs "bubble" idle time. Frontier runs compose all three (3D parallelism).

Mixed precision: what's actually stored in what, and why bf16 over fp16?

Compute (matmuls, activations) in 16-bit; weights also kept as an fp32 master copy that the optimizer updates — because per-step updates (lr × grad ≈ 1e-7 × values) underflow 16-bit accumulation. bf16 keeps fp32's 8-bit exponent (same range, less mantissa), so it tolerates large/small values without the loss-scaling machinery fp16 needs — fewer failure modes, hence the industry default on A100+/TPUs. Memory irony: mixed precision INCREASES weight-related memory (16-bit + 32-bit copies) — you pay memory for speed.

Gradient accumulation vs bigger batch — mathematically identical? Any gotchas?

Identical for the gradient itself: sum/mean of micro-batch gradients equals the big-batch gradient (linearity), as the 12-line proof shows. Gotchas: divide each micro-loss by accumulation steps (or average at the end); BatchNorm statistics differ per micro-batch (rarely relevant in transformers — LayerNorm is per-token, M5.5); some LR schedules/logging count steps differently; and wall-clock is longer (serial micro-batches). It buys batch smoothness, not throughput.

Why is gradient checkpointing a compute-for-memory trade and when is it worth it?

Backprop needs forward activations (M3.4); checkpointing stores them only at layer boundaries every √L layers and recomputes the rest during backward — activation memory drops ~√L-fold for roughly one extra forward pass (~30% compute). Worth it when activations dominate the memory bill: long sequences, big batches, large models on small cards — i.e., almost every consumer-GPU fine-tune. Not worth it when compute-bound with memory to spare.

What makes frontier-scale training an infrastructure problem, not just an ML problem?

At 10k+ GPUs: MTBF arithmetic makes failures continuous (Llama-3's ~466 interruptions in 54 days), demanding automated checkpoint/resume; checkpoints are terabytes (storage bandwidth becomes a bottleneck); network topology dictates the parallelism layout; loss spikes require automated detection and batch-skipping; and data pipelines must feed millions of tokens/sec. The ML (architecture, objective) is settled before launch — the campaign is distributed-systems engineering. Recognizing this division is what the question tests.
