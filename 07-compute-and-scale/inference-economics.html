Inference Economics

Module capstone, and the page closest to your invoices. Training happens once; inference is forever — and its costs have a precise anatomy: two phases with opposite bottlenecks, a pricing asymmetry you've already paid without knowing why, and one serving trick (continuous batching) that decides whether a GPU serves 3 users or 40. By the end, you'll price your own RAG queries from first principles.

Two phases, opposite bottlenecks

M5.7 split generation into prefill (the whole prompt in one parallel pass) and decode (one serial pass per output token). The systems view adds the crucial detail: they stress different hardware limits. Prefill is compute-bound — big (n × d) matmuls saturate the cores; the GPU is genuinely busy. Decode is memory-bandwidth-bound — to produce ONE token, every one of the model's ~16 GB of weights must be read from VRAM into the compute units, for a comparatively tiny matmul. The chip spends decode-time waiting on memory, not computing. This single asymmetry explains most of serving engineering.

Why output tokens cost 3–5× input tokens

Now the pricing sheet decodes itself. Input (prefill) tokens amortize beautifully: thousands processed per weight-read, hardware saturated, cheap per token. Output (decode) tokens each demand a full pass with terrible hardware utilization — plus they hold the GPU (and a growing KV cache, M11.2) for the whole generation. Providers price accordingly: input cheap, output dear. Design consequence you can apply tomorrow: fat prompts are far more affordable than fat outputs — stuffing 10 retrieved chunks into context costs less than asking for a needlessly verbose answer.

Continuous batching: the trick that made serving profitable

Naive serving runs one conversation per GPU — and decode's bandwidth-boundness means 95% idle compute. The fix mirrors M7.1: batch many users' decode steps together — one weight-read serves 40 conversations' next tokens simultaneously. The refinement that made it practical (vLLM's continuous batching): don't wait for a batch to finish together; as any conversation completes, its slot is instantly refilled by a waiting request — a conveyor, not a bus. Add paged KV-cache memory management and GPU throughput rises ~10–25× versus naive serving. This, more than any model improvement, is why per-token API prices fell ~100× in three years.

Real numbers: pricing one of your RAG queries

Anatomy of a typical query — embed the question (MiniLM, self-hosted: ~$0.000001, effectively free) → vector search (infrastructure, ~free at your scale) → LLM call: 2,000 input tokens + 300 output. At representative mid-tier API prices (~$0.25/M input, ~$1.25/M output): input $0.0005 + output $0.000375 ≈ $0.0009 per query — the output's 300 tokens cost nearly as much as the input's 2,000 (the 3–5× asymmetry, live). At 100k queries/month: ~$90. Doubling retrieved context: +$50/mo. Halving answer length: −$19/mo and faster. You can now do this arithmetic for any provider's price sheet.

Connect the dots

Behaviors you've observed, now explained: the long pause before the first word on big prompts (prefill of YOUR fat RAG context), then smooth streaming (decode's steady drip); why max_tokens caps cost meaningfully but prompt trimming often matters less than you'd think; why batch-embedding your corpus was cheap but the LLM layer dominates your bill. And a strategic one: M7.4's "overtrained small models" exist precisely because decode cost scales with parameters — the whole industry is arranged around this page's asymmetry.

Build: a cost model for your actual pipeline
def rag_query_cost(input_toks=2000, output_toks=300,
                   price_in=0.25, price_out=1.25,      # $ per million tokens
                   queries_per_month=100_000):
    per_query = input_toks/1e6*price_in + output_toks/1e6*price_out
    monthly = per_query * queries_per_month
    print(f"per query: ${per_query:.6f}  |  monthly: ${monthly:,.0f}")
    print(f"  input share : {input_toks/1e6*price_in/per_query:5.1%}")
    print(f"  output share: {output_toks/1e6*price_out/per_query:5.1%}")

rag_query_cost()                                   # baseline
rag_query_cost(input_toks=4000)                    # double the retrieved chunks
rag_query_cost(output_toks=150)                    # tighter answers
rag_query_cost(price_in=3.0, price_out=15.0)       # frontier-model prices

Plug in your real token counts (your API logs have them) and provider prices. The output-share line is the punchline for most teams: verbosity is a line item. Then try the frontier-price row and understand why model-tier choice (M6.5's decision) is usually the biggest knob on the whole bill.

If you remember one thing

Inference = compute-bound prefill (sets first-token latency, cheap per token) + bandwidth-bound decode (sets streaming speed, expensive per token — hence the 3–5× output premium). Continuous batching packs many users into each weight-read and is why serving economics work at all. Training is a one-time cost; this page is the perpetuity — design your prompts, outputs, and model tiers around it.

Interview questions

Why is LLM decode memory-bandwidth-bound rather than compute-bound?

Generating one token requires reading ALL model weights from VRAM (every layer participates) to perform relatively small matmuls (batch 1 × one position). Arithmetic intensity (FLOPs per byte moved) is far below the GPU's compute/bandwidth ratio, so the cores idle waiting on memory — an H100 doing single-stream decode may use <5% of its FLOPs. Prefill, processing thousands of positions per weight-read, has high arithmetic intensity and is compute-bound. Remedies for decode: batch users (share the weight-read), quantize (fewer bytes, M11.3), speculative decoding.

Explain the input-vs-output token pricing asymmetry from first principles.

Input tokens are processed in parallel prefill — thousands per full weight-read, hardware saturated, low marginal cost. Each output token needs its own serial, bandwidth-bound pass, occupies the GPU and KV-cache memory for the generation's duration, and limits batching flexibility. Provider cost per output token is genuinely several times higher, and pricing (3–5×) mirrors it. Design corollary: rich context is cheap, verbose generation is not — push work into prompts, constrain outputs.

What is continuous batching and why was it such a leap?

Serving technique (popularized by vLLM/Orca): compose each decode step's batch dynamically across active conversations — when any sequence finishes, immediately admit a queued one, rather than waiting for whole-batch completion. Combined with paged KV-cache allocation (fragmentation-free), it keeps the weight-read amortized across a full batch at all times: ~10–25× throughput over static batching, directly translating to the ~100× per-token price drops of 2022–2025. It attacks decode's bandwidth-boundness with M7.1's batching principle, applied continuously.

Your product's time-to-first-token is bad but streaming is smooth. Diagnose and fix.

TTFT ≈ queueing + prefill; smooth streaming means decode is fine. Suspects: prompt too large (your RAG stuffing — trim/rerank chunks harder, M12.2), cold model loading, queue contention at the provider, or no prefix caching (many providers/servers cache shared system-prompt prefixes — restructure prompts so the static part leads and stays byte-identical). Measure: log prompt tokens vs TTFT correlation; if linear, it's prefill — cut context or pick a faster tier. The question tests whether you map user metrics onto the two phases.

Self-host an 8B or call an API — how do you frame the decision quantitatively?

Compute both cost curves: API = tokens/month × prices (linear, zero fixed cost, elastic). Self-host = GPU cost (e.g., ~$1–2/hr for a 24–48 GB card) ÷ achievable throughput (with continuous batching, maybe 1–5k tokens/s aggregate) → cost per M tokens, plus engineering time. Break-even typically lands at sustained utilization: bursty/low volume → API wins; steady high volume, latency control, or data-locality needs → self-host wins. State the assumptions (utilization %, batching efficiency) — the framework matters more than the number.
