Model Memory Math

The most practically useful arithmetic in this course. "Will it fit on my GPU?" decides what you can run, fine-tune, and afford — and it's all multiplication you can do on a napkin. By the end of this page you'll price any model's memory in seconds, know exactly why training needs ~8× what inference does, and understand the OOM error as a line item rather than a mystery.

Inference: parameters × bytes

weights memory = parameter count × bytes per number
The bytes menu: fp32 = 4 · fp16/bf16 = 2 · int8 = 1 · int4 = 0.5. So the rule of thumb everyone uses: a 7B model ≈ 14 GB in fp16, 7 GB in int8, 3.5 GB in int4. (Add ~10–20% overhead for activations, KV cache and runtime — the "why won't 14.0 fit in 14.0" tax.)

The OOM playbook

When CUDA-out-of-memory strikes, the itemized bill tells you which knob does what: smaller batch (shrinks activations linearly — first move, costs only wall-clock via gradient accumulation, M7.3); shorter sequences (activations scale with seq length; attention's n² even faster); gradient checkpointing (drop cached activations, recompute in backward — ~30% compute for big memory savings); LoRA/QLoRA (eliminate gradients+optimizer for frozen weights — the whole M8.5 story); quantize the base (halve or quarter the blue bar, M11.3); and only then, more/bigger GPUs. Reading the error as "which bar overflowed?" replaces superstition with debugging.

Real numbers: the napkin, applied

Fits-on-what table (fp16 weights + headroom): MiniLM 22M → 0.05 GB, runs anywhere including phones. 1B → 2 GB: any laptop GPU. 7–8B → ~16 GB: RTX 4090 / T4-tier, or 5 GB at int4 (Ollama's trick). 70B → 140 GB: 2×A100-80 fp16, or ~40 GB int4 (one big card, tight). 405B → 810 GB: a cluster, full stop. And the training column: multiply by ~7–8× for full fine-tuning — which is why "we fine-tuned 70B" implies a GPU cluster, but "we QLoRA'd 70B" fits one node.

Connect the dots

Now several things you've heard snap into arithmetic: why Ollama downloads are ~4–5 GB for "7B" models (int4: 7 × 0.5 + overhead); why Colab's free T4 (16 GB) fine-tunes 7B only via QLoRA; why M5.6's parameter counting was worth learning (params → bytes is one multiply); and why your embedding model never troubles any machine (0.05 GB!). One more: the KV cache — conspicuously absent from today's bill — becomes the dominant inference cost at long context, and that's exactly M11.2's opening scene.

Build: the memory calculator (keep this function forever)
def memory_gb(params_b, precision="fp16", mode="inference",
              batch=8, seq=2048, layers=32, hidden=4096):
    bytes_per = {"fp32": 4, "fp16": 2, "bf16": 2, "int8": 1, "int4": 0.5}[precision]
    weights = params_b * bytes_per                       # the blue bar

    if mode == "inference":
        return round(weights * 1.15, 1)                  # +15% runtime overhead

    grads     = params_b * 2                             # bf16 gradients
    adam      = params_b * 8                             # 2 × fp32 moments
    master    = params_b * 4                             # fp32 master weights
    acts      = 1.2e-4 * batch * seq * layers * hidden / 1e9 * 2   # rough, GB
    return round(weights + grads + adam + master + acts, 1)

for m, p in [("MiniLM", 0.022), ("Llama-8B", 8), ("Llama-70B", 70)]:
    print(f"{m:10s} run fp16: {memory_gb(p):6.1f} GB | "
          f"run int4: {memory_gb(p, 'int4'):6.1f} GB | "
          f"full train: {memory_gb(p, mode='train'):7.1f} GB")

Sanity-check its outputs against the table above, then use it for real: next time anyone asks "can we fine-tune X on our hardware?", you answer in ten seconds with a breakdown, not a shrug. (The activation term is a rough estimate — batch and seq are your levers; watch them move the total.)

If you remember one thing

Inference = params × bytes (+15%). Training ≈ 7–8× that, itemized as gradients + Adam's two moments + fp32 masters + cached activations. Every OOM error is one of those bars overflowing, and every memory trick in the field — quantization, LoRA, checkpointing, batch shrinking — is named by which bar it attacks. Napkin math beats folklore.

Interview questions

How much memory to RUN a 13B model? To fully FINE-TUNE it?

Run: 13B × 2 bytes (fp16) = 26 GB + ~15% overhead ≈ 30 GB → one A100-40 or two 24 GB cards; int4 gets it to ~8 GB. Full fine-tune with Adam + mixed precision: weights 26 + grads 26 + optimizer 104 (fp32 moments) + fp32 masters 52 + activations ≈ 210+ GB → multi-GPU with sharding, or LoRA to collapse the training-state terms. Showing the itemization, not just the total, is the differentiator.

Why does Adam specifically inflate training memory?

It stores two persistent statistics per parameter (exponential averages of gradient and squared gradient — M3.5's momentum and magnitude), conventionally in fp32 for numerical stability: 8 bytes/param, versus 2 for the bf16 weights themselves — the optimizer alone is 4× the model. Mitigations: 8-bit optimizers (bitsandbytes quantize the moments), Adafactor (factorized second moment), or freezing most parameters (LoRA — no gradients or moments for frozen weights at all).

What exactly are "activations" in the memory bill and what controls their size?

The intermediate tensors from the forward pass that backprop needs to compute local slopes (M3.4) — roughly every layer's inputs/outputs, so ∝ batch × seq_len × hidden × layers (attention's n×n maps add a quadratic seq term). Controls: batch size (linear), sequence length (linear-to-quadratic), gradient checkpointing (store 1/√L of them, recompute the rest — ~30% extra compute), and activation-precision choices. It's the only training-memory term that DOESN'T scale with parameter count — which is why small-batch tricks rescue big models.

Your 7B fine-tune OOMs on a 24 GB card. Give the escalation ladder.

(1) Confirm the bill: full FT needs ~100 GB — it was never going to fit; set expectations. (2) LoRA: freeze base (14 GB fp16), train ~0.1% adapters — fits with modest batch. (3) QLoRA: 4-bit base (~4 GB) + LoRA — comfortable, batch headroom back. (4) Within any setup: reduce batch + gradient accumulation, cap sequence length, gradient checkpointing, 8-bit optimizer. (5) Only if quality demands full FT: multi-GPU sharding (M7.3's ZeRO/FSDP). The ladder shows you optimize technique before hardware.

Why can a phone run a 3B model but not train a 100M one comfortably?

Inference is weights-only and streaming-friendly: 3B int4 ≈ 1.5 GB, feasible in mobile RAM with quantized kernels. Training multiplies memory (grads + optimizer + activations ≈ 4–8×), needs backprop's cached activations, higher precision for stability, and sustained compute/thermals phones can't hold. Asymmetry rule: inference cost ∝ params; training cost ∝ params × optimizer-state × activation budget — different regimes, different hardware classes.
